# mailproof - Integration Guide

## What this is

mailproof records a re-checkable proof of each email in a **two-party (A to B) exchange** in a local git trail: the signed headers, never the body (since 3.0.0 the raw email and attachments are also kept in a local content store outside git, on by default and expiring; `forget` removes content only, proofs are permanent). The sender's DKIM public key is archived at capture, so anyone can verify the record offline, years later, after the key has left DNS. Pure ESM, Node >= 22.19, runtime deps `mailauth` + `mailparser` + `imapflow` (only for `sync`) + `better-sqlite3` (only for `list` and `copies`). Wire formats: `docs/product/SPEC.md` Part B (repo only).

## What mailproof is and is not

- It is a recorder and an offline verifier: `record`, `verify`, `matchBody`, `matchFile`, `check`, `list`, `describe`, `verifyWith`, `counterparties`, `linked`, `checkProfile`, `proofParts`, `get`, `replyText`, `replyFacts`, `rawEmail`, `attachment`, `expireContent`, `forget`, and a read-only IMAP fetcher in front of `record`: `sync`.
- It is not a mail client, a sender, a web UI or a multi-party workflow engine (those are gitdone/signedreply.com), not proof of delivery, and not a claim of legal admissibility.
- It produces a verdict; acting on it is the consumer's job.

## Which entry point do I need?

- One-off verdict on an email, nothing written -> `check(raw)`.
- Record mail your own pipeline receives (for example a Postfix pipe) -> `record(raw, { direction, source, envelope })`; map `ERR_TRAIL_LOCKED` to exit 75.
- Capture a mailbox over IMAP -> `sync(...)`, the `mailproof` CLI (`mailproof sync`, `mailproof watch`; read it by person: `mailproof people`, `mailproof show b@example.com`, `mailproof verify b@example.com`), or `mailproof-sync` under cron or a systemd timer.
- Re-check later or elsewhere, offline -> `verify(id)`, or `verifyRecord(record)` with no trail.
- Read what a sender newly wrote in a recorded reply -> `replyText(raw)`, then apply the decision rule in "Reading a reply" below.
- Learn what the people you wrote to answered (an approval, an acknowledgement) -> `replyFacts({ messageId })` (the Message-ID of your request), or `replyFacts({ address })` for everything one person answered, then apply the rule in "Approvals" below.
- Build an agent tool menu -> `primitives.json` (25 primitives) plus this file.

## Minimal usage

```js
import { Mailproof } from 'mailproof';

const mp = new Mailproof({ trailDir: './trails' });
const { id } = await mp.record(rawEmailBytes, { direction: 'in', source: 'imap' });
const v = await mp.verify(id);          // offline, from the record alone: v.ok, v.trust
```

```js
import { Mailproof, verifyRecord, hashDocument, TRUST_LEVELS, RULES_VERSION } from 'mailproof';
```

## All options: `new Mailproof(opts)`

| Option | Meaning |
|---|---|
| `trailDir` (required) | Directory holding trails. Each trail is a git repo at `<trailDir>/<trail>/`. |
| `trail` | Trail name, `/^[a-z0-9][a-z0-9_-]{0,63}$/`, default `default`. |
| `resolver` | mailauth-compatible DNS resolver `(name, type) => [[txt]]` (tests inject one). A lookup it has not answered within 5 s is answered as the error `dns timeout` (`code: 'ETIMEOUT'`); one message's lookups together may wait 30 s, then further ones fail at once the same way. It must return plain data, as `node:dns` does; anything else is a DNS error (`code: 'EBADRESP'`). |
| `otsBin` | The `ots` (OpenTimestamps) binary. Absent = **on** (`ots` from `PATH`; since M4); a string = on, that binary; `null` = off (no manifest, no stamp, `record()` says `ots: 'off'`). |
| `stamp` | `{ mode?: 'batch'\|'record', everyHours?: 1..720 }`. `batch` (default): `record()` never runs `ots` and returns `ots: 'queued'`; the stamp job (below) seals new records in one manifest. `record`: the 3.3.0 per-record stamp inside the trail lock. Unknown keys throw. |
| `now` | Clock `() => Date`. |
| `trustedSealers` | ARC sealer domains whose chains may yield live `forwarded`. |
| `lockTimeoutMs` | How long `record()` waits for another writer of the same trail (default 30000). On timeout it throws `ERR_TRAIL_LOCKED` and writes nothing. |
| `worker` | The deadline backstop, default on: `{ size: 1, cpuMs: 15000, wallMs: 120000, maxMemoryMb: 1536 }`. `check()`/`record()` build in a warm worker thread that is killed over 15 s of its CPU, 120 s of busy wall time (DNS excluded) or 1,536 MB; the message is then recorded `unverified`, `over limit: time` / `over limit: memory`. `size: 0` builds in-process with no backstop. |

All methods are bound: `const { verify } = mp` works. `await mp.close()` stops the worker threads early; it is never needed for the process to exit. With a worker, a `record()`/`check()` still running when `close()` is called (or when the last instance sharing the pool closes) may reject, and if it rejects that message is not recorded: await in-flight calls first.

## Public API

- `check(raw, { envelope? })` -> `{ live, portable, signatures, unsigned, partial_body, key_errors, body_status, body[] }`. Writes nothing. Judged as of now.
- `record(raw, { direction: 'in'|'out', source?, envelope? })` -> `{ id, duplicate, commit, record?, ots?, content? }`. One commit per record. `content` (absent with `content.store: false`) is `{ stored, attachments, error? }`: whether the raw email and attachments were kept in the local content store; a failed content write never loses the proof. Never throws on unverifiable mail (it is recorded `unverified`); throws on empty input, a bad `direction`, a git failure, or `ERR_TRAIL_LOCKED` (another writer held the trail longer than `lockTimeoutMs`; nothing is written, retry later). The same bytes captured again return `duplicate: true` and write nothing; a copy with any byte difference is a new record. `ots` is `'off'`, `'pending'` or `{ error }` (an OTS failure never blocks the commit).
- `verify(recordOrId, { at? })` -> `{ ok, trust, basis, at, engine, signatures[] }`. Offline, from the record alone. `at` defaults to the record's `captured`; a missing or garbled `captured` fails closed. `trust` is recomputed now.
- `matchBody(recordOrId, raw?)` -> `{ match, full, signatures[], reason? }`. `full` = body matches `bh=` AND the signature verifies at capture time. Omit `raw` to use the stored raw email (content store); no usable content gives `match: false` and a `reason`.
- `matchFile(recordOrId, bytes)` -> `{ match, attachment }`.
- `list({ limit?, direction?, with?, role?, before?, after? })`, `get(id)`. `with` is one exact address (trimmed, case-insensitive; `bob@gmail.com` is not `bob@company.com`, `@domain` is not an address), `role` (`from|to|cc|reply-to`, needs `with`) narrows it, `after` inclusive / `before` exclusive on `captured`. A wrong type throws a TypeError. Each row is `{ id, captured, direction, live, portable, message_id, from, to[], subject, subjectSource, addresses[] }`: `from` the first From address, `to` every To address (header order), `subject` decoded with `subjectSource` `'signed'` (a signature that verifies covers it), `'claimed'` (only the sender's word: a failing signature covers it, or, for unsigned mail, it was read from the stored raw email, up to 500 such rows per call) or null; `addresses[]` is `{ role, address, signed, coverage }`. **`addresses[].signed` means covered by some signature, not that it verified; use the verdicts or `coverage`** (`'signed'` a verifying signature covers the line, `'failing'` only signatures that do not verify, `'none'`). Say "signed" to a person only for `coverage: 'signed'`. `get(id)` returns the record verbatim (its `addresses[].signed` is the weaker field).
- **Counterparties, links, profiles (M3 step 2, SPEC B8).** All read the record alone (never the content store) through the trail index.
  - `counterparties({ limit? })` -> `[{ address, records, first, last, verified }]`: one row per exact lower-cased address, most recently seen first; `verified` counts the RECEIVED records naming it whose live trust is `verified`. The trail owner is in it (a record does not say which address is yours).
  - `linked(id, { limit? })` -> `{ id, message_id, parents: [{ id|null, message_id, via, strength }], children: [{ id, message_id, via, strength }], more } | null`. `children` is cut at `limit` (default 1000) and `more` is `true` when it was. `via` is `in-reply-to` or `references`; `strength` is `signed` (a verifying, From-aligned DKIM signature covers the header that names the id) or `unsigned` (present only unsigned, or under a failing signature; Microsoft does not sign threading, F11). It reports what looks linked, never "the chain"; other copies of one message are `copies()`.
  - `checkProfile(record, profile, { at?, parent? })` (pure, exported like `verifyRecord`) and `mp.checkProfile(recordOrId, profile, opts?)` -> `{ ok, failed: [{ rule, want, got }], record, rules }`. Profile keys, all optional, unknown keys throw `ERR_BAD_PROFILE`: `senders: ['bob@x.com', '@gmail.com']` (matches the DKIM-aligned signed From only; an unsigned From never satisfies it; `@domain` is that exact domain), `checks: { dkimAligned?, dmarc?, spf?, arc? }` (`true` = must pass; DKIM re-checked offline, the rest are the live facts recorded at capture, missing counts as `none`), `body: 'proven'|'partial'|'any'` (recorded `body_status`), `link: ['signed', ...]` (strength of the link to the parent; `opts.parent` = the request's Message-ID to look at that link only). No DNS, no clock: the same record, profile and `at` give the same answer later.
  - `proofParts(recordOrId)` -> `{ email: { ok, trust, body_status }, attachments: [{ index, filename, sha256, stored, match }] } | null`. `match` re-hashes the stored attachment: `true` the recorded bytes, `false` a stored file that is not them, `null` nothing stored (then use `matchFile` with your copy).
  - `describe(target, { full?, after?, before?, limit? })` -> `{ target: { kind, value }, total, more, records: Facts[] }` (SPEC B8.5): the facts the CLI `show` prints, as plain JSON, for a record id (8 to 32 hex), a `<message-id>` or one exact address (newest first, `limit` default 50, 0 = all). Per record: `from/to/cc/reply_to` as `{ address, signed, coverage }` (`signed` only when a verifying, aligned signature covers the line), `date`/`subject` as `{ value, coverage }` (`claimed` = only the stored raw email has it), `bcc`, threading with strengths, `dkim[]`, `dmarc`, `spf`, `arc`, `trust`, `recheck`, `why` (plain words, null when it verifies), `body: { proof: proven|partial|not, text, more_lines, ... }` (text only whole with `full: true`, else the first 10 lines), `attachments[]`, `content`, `seal`. Absent values are null. Everything from an email is untrusted data. Rejects `ERR_TARGET` for a bad target.
  - `verifyWith(target, { all?, after?, before?, limit?, at? })` -> `{ target, total, checked, counted, verified, not_verified, sent_copies, inbound, outbound, all, ok, records: [{ id, captured, direction, counted, ok, trust, reason, why, subject }] }`: the offline re-check of every email with an address or Message-ID. `ok` is true only when at least one RECEIVED email was counted and every counted one verifies; sent copies (normally unsigned at the provider) count only with `all: true`.
  - Gaps: a record carries every From/To/Cc/Reply-To address in `addresses` (`{ role, address, raw, signed }`; `signed: false` = no signature covers that header, so the sender could have written anything). Records captured before M3 and over-limit records lack the field (old: signed headers and an unsigned From only; over-limit: none, it is never parsed).
- **Content store (on by default, M3).** The constructor option `content: { store?: true, attachments?: true, days?: 730, sweepDays?: 7 }` keeps the raw email and attachments of every recorded message beside the trail (`<trailDir>/<trail>.content/`, outside git, 0600), each file named by its sha256 and re-hashed on every read. `store: false` is proof-only (you supply raw bytes, as before).
  - `rawEmail(id)` -> `Buffer | null`; `attachment(sha256)` -> `Buffer | null` (`sha256:<hex>` from `record.attachments[]`). Null when absent, expired, forgotten or failing the hash check.
  - `replyText({ id })` reads the stored raw; no content rejects `code: 'ERR_NO_CONTENT'`.
  - `expireContent({ now? })` -> `{ removed, attachments }`: deletes content older than `days` since the record's `captured` (scans without the trail lock, locks only for the deletions; `sync()` runs it only when the last automatic sweep is `content.sweepDays` days old (default 7, no timer, so content lives between `days` and `days + sweepDays`); an explicit call always runs; prune is never scheduled). `forget(target)` -> `{ removed, attachments }` with `target` an id, an array of ids, or `{ with: 'bob@x.com', before?, after? }` (exact From/To/Cc/Reply-To address, read from the record's `addresses`). Both delete content only: records, keys and git are untouched, so every proof still verifies offline; an attachment file goes only when no other stored email lists it. Both take the trail lock.
  - `prune({ before, deleteBackup? = false, dryRun? = false, now? })` -> `{ cutoff, noop, dryRun, previousHead, head, removed, kept, stragglers: [ids], dropped, keysCarried, reverify: { ok, failed: [ids] }, backup, content: { removed, attachments, error? }, timing }` (M3 step 3, SPEC B9): removes every record captured before `before` (records, reply-text records, `.ots`, archived keys no kept record names, and their stored content). Explicit and rare, never scheduled: it rewrites history (kept proofs, keys, stamps and commit messages/authors/dates are byte-identical, only commit ids change; the first commit becomes a prune notice with the counts). A pruned copy is built beside the trail **without the trail lock** (writers carry on) and swapped in under a short lock; the old trail stays as `<trail>.pre-prune-<YYYY-MM-DD>` until you delete it (`deleteBackup: true`, or `rm -r`): the removal is only real after that. Only a prefix of history goes: a record captured before `before` that was committed after a later one is kept and listed in `stragglers`; `dropped` counts reply-text commits for removed records. A `before` that removes nothing is `noop: true` (no rewrite, no backup); one after the last record is refused (`ERR_PRUNE_CUTOFF`). `reverify` re-checks every kept record offline; a failure is listed, never a reason to stop. After the swap the sync cursor follows the new HEAD (so `sync()` does not record the removed mail again) and the index rebuilds by itself. Crash-safe: a killed prune leaves exactly the old or exactly the pruned trail, finished by the next call that takes the trail lock. Errors: `ERR_PRUNE_RUNNING` (another prune), `ERR_SYNC_LOCKED` (a sync outlasted the wait), `ERR_TRAIL_LOCKED`, `ERR_PRUNE_CUTOFF`, `ERR_PRUNE_REWRITTEN` (history changed during the build, run it again), `ERR_PRUNE_VERIFY`, `ERR_PRUNE_JOURNAL`. Time is about quadratic in the commit count on git's side; disk needs a second copy of the kept trail. `dryRun: true` runs the same plan and re-check and returns the same shape (`dryRun: true`, `head: null`, `backup` the path a real prune would use) without building, swapping or writing anything.
  - `stamp()` -> `{ enabled, mode, ran, skipped?, manifests: [{ seq, records, replies, sha256, commit }], stamped, unstamped, unsealed, upgraded, pending, error? }` (SPEC B13.1): the stamp job. Writes `manifests/<seq>.json` (sha256 of each record and reply-text file added since the last one, chained by the previous manifest's hash), stamps the newest manifest once, upgrades older pending proofs. `sync()` runs it at the end when due (`SyncResult.stamp`; every `stamp.everyHours`, marker `.<trail>.stamp.json`); a pipe-only consumer schedules `mailproof stamp`. Network only here and in `sync()`, never in `record()`. A missing `ots` returns the plain `error` and never throws; throws `ERR_STAMP_LOCKED`, `ERR_TRAIL_LOCKED`, `ERR_STAMP_CHAIN`.
- `status()` -> `{ trail, records: { total, totalSource, in, out, oldest, newest, verified, unverified } | { error } | null, content: { files, bytes } | 'off', index, pendingStamps, seal }`: what the trail holds and how it is kept, read-only and offline (no lock, never builds the index); the CLI and the MCP `status` add the state-file facts (last sync, last backup, watch).
- `backup({ out?, withContent?, push?, remote?, dryRun?, mkdir? })` -> `{ dryRun?, bundle, bytes, commits, content: { path, bytes } | null, contentNote?, contentError?, pushed: { remote, host, refs } | null, pushError?: { kind, message } }` (SPEC B11.6): a git bundle of the trail (made under the trail lock, verified, 0600, never overwrites), optionally the content store as an unencrypted `.content.tar`, optionally a push of the trail to `remote` that is never forced; credentials in a remote URL are hidden everywhere. A failing tar or push is a field, not a rejection.
- `export({ with: string[], after?, before?, out, tar?, dryRun? })` -> `{ out, bytes, files, head, bundle_sha256, records, replies, keys, manifests, seals: { anchored, pending, unstamped, unsealed }, content: { stored, absent } }`, with `dryRun: true` also `dryRun: true` and `selection[]` and nothing written (SPEC B13.2, B13.2.1a): a pair bundle, a directory (or one `.tar`) of byte-identical copies of the committed records, reply-text records, archived keys and the manifests and `.ots` proofs their seals need, plus `bundle.json` (an index, not a proof) and `README.txt`. A record is included when it names **any** of `with` on From, To, Cc or Reply-To (a union), captured in `[after, before)`. No bodies, attachments, other records or keys. Read-only on the trail (no lock while reading, no commit, no `ots`, no network): it pins a commit, and the index only proposes ids that are re-tested against the records. `out` must not exist or be an empty directory you own, never inside the trail or content store; mode 0700/0600. Self-checked with `verifyBundle` before delivery. Never stamps: run `stamp()` first. Errors: `ERR_EXPORT_EMPTY`, `ERR_EXPORT_TOO_BIG` (10,000 records or 256 MiB), `ERR_EXPORT_EXISTS`, `ERR_EXPORT_REWRITTEN` (a prune during the read: retry), `ERR_EXPORT_SELF_CHECK`, `ERR_EXPORT_TAR`, `ERR_STAMP_CHAIN`, `ERR_TRAIL_LOCKED`, `ERR_INDEX_UNAVAILABLE`. Not an MCP tool. It proves the signed headers and (when anchored) the record's existence by a time; it proves nothing about completeness, bodies, or when mail was received.
- `verifyBundle(dir, { ots?, expect?, strict? })` (a standalone function, not a method; SPEC B13.3) -> `{ ok, failed[], bundle, expect, files, records[], chain, ots, counts }`. The recipient's check, with no trail, index, account or network: `verifyRecord` per record, the files against `bundle.json`, keys, selection, replies, the manifest chain and each seal by `ots info` (local; never `ots upgrade` or `ots verify`). A seal is `anchored` (a Bitcoin block attestation for exactly these bytes; the header is NOT checked against Bitcoin), `pending`, `unstamped`, `unsealed`, `unchecked` (no `ots`) or `bad`. Lenient by default (unverified records and pending seals are reported); `strict` also fails unless all are verified and anchored. Hostile-input safe (no symlinks, FIFOs or traversal; size and count caps). Never rejects for a bad bundle, only a `TypeError` for a bad argument. A record the exporter called `unstamped` shows as `unsealed` to the verifier (the bundle carries no manifest for it).
- `upgradeStamps()` -> `{ enabled, upgraded, pending, error? }` (SPEC B3): folds the Bitcoin attestation into calendar-pending OpenTimestamps stamps (`otsBin` set), one trail-lock window per stamp, each upgraded proof committed on its own; asks only about stamps not yet known anchored (a sidecar cache beside the trail). No `otsBin`: `{ enabled: false, upgraded: 0, pending: 0 }`; a missing or hung `ots` binary is reported in `error`, never thrown.
- `sync({ host, port?, user, auth: { pass } | { accessToken }, folders?, sent?, maxMessages?, maxBytes?, tls?: { ca } })` -> `{ complete, folders: [{ folder, direction, attempted, uidvalidity, reset, last_uid, seen, recorded, duplicate, over_limit, skipped[], bytes, complete, error }] }`. Reads one mailbox over IMAP (implicit TLS, certificate always checked, `EXAMINE` + `BODY.PEEK`, so nothing is marked seen, moved or deleted) and `record()`s each message: `folders` (default `['INBOX']`) as `in`, the `\Sent` folder (`sent: true`, default; a path string; `false` skips) as `out`, `source` `imap:<folder>`. One account per call; you obtain and refresh an OAuth token yourself. A resume cursor is kept in `<trailDir>/.<trail>.sync.json` beside the trail (not in git); caps per folder per run are 1,000 messages and 512 MiB (options can only lower them) and 30 minutes per call, so loop until `complete` is true. A trail restored from an older backup or replaced is detected (the cursor records the trail's HEAD) and the folders rescan with `reset: 'trail'`; no manual step. A re-fetched message has the same bytes, so it is `duplicate`, never a second record. Over 25 MiB: streamed through a hash and recorded `over limit: total_bytes`; over 128 MiB: in `skipped`. Provider Sent copies are unsigned, so they record `unverified`. No envelope on IMAP, so `authorized` cannot occur. Throws a TypeError for bad options, then only `ERR_IMAP_AUTH`, `ERR_IMAP_CONNECT` or `ERR_SYNC_LOCKED` (a second `sync` on the trail: fails at once); everything else is in a folder's `error` (`ERR_IMAP_NO_FOLDER`, `ERR_IMAP_NO_SENT`, `ERR_IMAP_PROTOCOL`, `ERR_IMAP_TIMEOUT`, `ERR_IMAP_THROTTLED`, `ERR_IMAP_UIDVALIDITY`, `ERR_TRAIL_LOCKED`). The first trail error stops the run. The credential is never logged, returned or stored. Leave OTS off for a backfill.
- `copies(idOrKey)` -> `{ message_key, original, copies[], contained_in[] }`: every recorded copy of one signed message (the id is the raw-bytes hash, so a list-relayed or forwarded copy is its own record; `message_key` groups them), the derived `original` (earliest `direct` copy with a matched body), and the records (forwards, list digests) that carry it as an attached original. Each record has `copy: { kind: direct|relayed|forward|digest|unknown, evidence }`.
- `list` and `copies` read a rebuildable SQLite index kept beside the trail (`<trailDir>/.<trail>.index.sqlite`, not in git, safe to delete; opened for each call and closed before it returns, so nothing stays open between calls and `close()` has nothing to do for it; built on the first call, then caught up from the trail's git HEAD on the next call after a `record()`). If the `better-sqlite3` native addon cannot load on the platform they reject with `code: 'ERR_INDEX_UNAVAILABLE'` (no fallback); `record`, `get`, `verify`, `matchBody`, `matchFile` and `sync` never need it. While the index catches up they wait on the trail lock (`ERR_TRAIL_LOCKED` after `lockTimeoutMs`). Equal `captured` values come in ascending id order. The index is navigation, not proof: re-check with `verify`.

`verifyRecord(record, { at? })` is the same offline check as a pure function, so a third party can verify an exported record with no trail.

Portable `verified` covers the signed headers; read `body_status` for the body. Each record carries `body_status` and, per signature, `body: { status, explain[] }` (`matched` / `partial` / `mismatch` / `not-checked`; `explain` entries `{ kind, detail }` are counts and domains only: `l_tag`, `appended`, `prepended`, `canonicalisation`, `line_endings`, `forwarded`, `mailing_list`, `search_capped`, `unknown`). It never changes a trust verdict.

## Reply text (`replyText`)

`replyText(raw)` -> `{ id, text, text_sha256, text_bytes, quote, trailing, source, boundary, stripper, body_status, proven, commit, duplicate }`. Give it the raw bytes of a reply you already recorded; it returns only what the sender newly wrote (quoted history removed), so a reply that merely quotes "Approve payment of $5,000?" is not read as an approval. Interpreting the text is yours; mailproof does not decide what a reply means.
- `proven` is true only when the recorded `body_status` is `matched` (the body matches the signed `bh=`) and the text came from a `text/plain` part. `partial` (an `l=` prefix), `mismatch` (for example Outlook/Exchange-received copies) and `not-checked` (unsigned, over limit, your own Sent copy) are unproven: the text is still returned, flagged.
- `quote`: `found` (a quote boundary was cut), `not-found` (none; the whole body is returned, never a guess), `inline` (answers written inside the quote; not merged). `trailing: true`: unquoted text follows the quote (a signature, or bottom-posted text) and is NOT in `text`; read the raw email if you need it. Signatures are not stripped.
- `source: 'html-only'`: no text/plain part, nothing extracted (`text` '', `proven` false).
- The stripper is versioned and deterministic (`mailproof-quote/1`): anyone with the raw email re-runs it and gets the same text and `text_sha256` (over its UTF-8 bytes). One small `reply-text` record (hash, byte count, flags, `body_status`, time; never the text, body or subject) is committed to `replies/<id>.mailproof-quote-1.json`; the same message again is `duplicate: true` and writes nothing. Show the text you acted on; its hash matches `text_sha256` in a commit dated before the action.
- Privacy: `text_sha256` of a short reply ("yes", "approve") is guessable by hashing candidates; the trail is as private as the people who can read it, and they can confirm a guessed short answer.
- Errors: `ERR_NOT_RECORDED` (record the message first), `ERR_OVER_LIMIT` with `err.limit` (nothing written), `ERR_TRAIL_LOCKED`. It runs in the worker pool like `record`. Known limits of `/1`: tested on English-style attributions and Outlook/Foxmail header blocks; the name after the verb (`... schreef Amr <a@x>:`) and, above a `>` run, any language's attribution line (ends in `:` with a year, hh:mm or `@`) are cut; a quote WITHOUT `>` marks in a language whose verb is not listed falls through to `not-found`. Wire format: `docs/product/SPEC.md` B6.

## Approvals and reply facts (`replyFacts`)

`replyFacts({ messageId })` (or `replyFacts({ address })`: every inbound direct reply that person sent to a message in the trail) -> an array of flat bundles (every value a string; SPEC B10.3 has the full table and closed sets), one per recorded inbound DIRECT reply to that Message-ID (its In-Reply-To names it, or it is the last entry of its References; later thread members are not included), earliest `captured` first; `[]` means no reply yet. Read-only (no trail write); text comes from the content store, so with no stored email `text`/`firstLine` are `""` and `textSource` is `none` (`content` | `none` | `over-limit`). mailproof sends nothing and decides nothing: you send the question from your own account (ideally with your own Message-ID), then poll `replyFacts` for it.
- Fields: `messageId`, `messageKey`, `recordId`, `commit`, `trail`, `captured`, `from`/`fromRaw` (lower-case / as written), `fromDomain` (the domain of `from`, lower-case, one trailing dot removed, `""` if none; a CLAIM: pair `fromDomain in [...]` with `fromDkimAligned in ["pass"]`, never a substring rule on `from`; subdomains are not folded; bareguard's `ignoreCase` needs bareguard `^0.34.0`), `fromDkimAligned` (`pass` = an aligned, offline-verifying DKIM signature covers From; `fail`; `none` = unsigned), `to`/`toRaw`/`cc`/`ccRaw` and `attachments` (joined with `,`, no space), `date`/`dateSource`, `subject`/`subjectSource` (`signed` = a verifying signature covers it, `claimed` = the raw email's header, `none`), `dkim` (`pass`/`fail`/`none`), `dmarc`/`spf`/`arc` (`pass`/`fail`/`none`/`other`), `live`/`portable` (TRUST LEVELS: `verified`, `forwarded`, `authorized`, `unverified`), `link` (`signed`/`unsigned`/`none`: is YOUR Message-ID in a signed In-Reply-To/References; Microsoft does not sign these), `text`, `firstLine` (first non-empty line after ECMAScript `trim`, no case folding), `textSource`, `bodyProven` (`proven`/`unproven`), `quote` (`found`/`not-found`/`inline`), `trailing` (`yes`/`no`: text written below the quote, not in `text`).
- Copies of one signed message (relayed, list-forwarded) are separate bundles with the same `messageKey`. Several different replies are several bundles; mailproof never picks.
- **Consumer rule (agreed with bareguard's session, 2026-11-10; yours to implement, not mailproof's):** group bundles by `messageKey` (an empty key is its own group), run your rubric on each distinct reply (for bareguard, `checkStep`; green = for example `firstLine` in your approval words (a word the user chose; bareguard's `in` rule matches exactly and case-sensitively by default, ruling #74; its opt-in `ignoreCase: true` folds case only, still whole value, so `Approved.` is not `approved`; tell the human in the question email to reply with exactly that word as the first line), `from` in your allowed addresses, `fromDkimAligned` `pass`, `bodyProven` `proven`, `link` `signed`), and ALLOW only when at least one distinct reply is green AND none is red. Zero replies, all red, or mixed is DENY. A second contradictory reply can deny an approval, never grant one. Audit reference: `mailproof:<recordId>@<commit>`.
- Errors: `TypeError` for a bad `messageId`; `ERR_TOO_MANY_REPLIES` past 200 direct replies; `ERR_INDEX_UNAVAILABLE` / `ERR_TRAIL_LOCKED` / `ERR_TRAIL_LAYOUT` as `list()`.

## Reading a reply: what each outcome means

| Field | Value | Meaning |
|---|---|---|
| `proven` | true | `body_status` is `matched` and the text came from `text/plain`: the words are exactly what the signing server sent. |
| `proven` | false | Words unproven; text is still returned, flagged. Causes: `partial` (only an `l=` prefix is signed), `mismatch` (body altered after signing), `not-checked` (unsigned, over limit, your own Sent copy), `source: 'html-only'` (text is ''). |
| `quote` | `found` | Normal: `text` is what sits above the quote boundary. |
| `quote` | `not-found` / `inline` | Whole body returned (never a guess) / answers written inside the quote, not merged. A human reads it. |
| `trailing` | true | Unquoted text follows the quote (signature or bottom-posted text) and is NOT in `text`. Read the raw mail if it matters. |

- **What stays proven when the body is not:** the sender domain and the signed headers (the portable verdict is unaffected). Threading ("this sender replied to that email") is proven only if the signer covers `In-Reply-To` in `h=`: Gmail does, Microsoft does not (an msn.com-signed reply has no signed threading even when its body matches).
- **The receiving rule:** mail received at Gmail keeps its body intact whoever sent it. Mail from outside received at Outlook/msn is altered by Microsoft, so `body_status` is `mismatch` and the words are unproven while the headers still verify. msn to msn matched once: a hint, not a rule. So replies whose words matter should be received at Gmail (or another mailbox that does not alter bodies) and captured with `sync`.
- **Decision rule for an agent:** `proven: false` -> show the text to a human, do not act on it alone. `trailing: true` -> more text sits below the quote; read the raw mail if it matters. `quote: 'not-found'` or `'inline'` -> a human reads it. Otherwise the text is the sender's new words, provably from that signed email; interpreting them is the consumer's job, mailproof never does.

## What leaves your machine

mailproof reads mail and writes proofs locally. Everything that goes over the network, with its off switch:

| Path | What is sent | To whom | Off switch |
|---|---|---|---|
| IMAP (`sync`, `watch`, `mailproof-sync`) | Your login and read-only requests for new mail (nothing is marked, moved or deleted). | Your mail provider, over TLS (certificates always checked). | Do not call `sync`; capture by pipe (`record`) needs no IMAP. |
| DNS (verification at capture: `check`, `record`) | Lookups of the sender's DKIM key, DMARC and SPF records. | Your DNS resolver. | None while capturing; `verify` and every read re-check offline, with no network. |
| OpenTimestamps calendars (the stamp job: `sync`, `watch`, `stamp()`, `mailproof stamp`) | One 32-byte hash of a manifest (a list of file hashes) per run, at most every `stamp.everyHours` (default 6). Never content, subjects or addresses. The calendars see your IP address and the timing. | Public OpenTimestamps calendars, through the `ots` command. | `otsBin: null` (library), `"ots": false` (account config), `MAILPROOF_OTS=off` (`mailproof-sync`). |

`record()`, `check()`, `verify()` and every read never contact the calendars: only `sync()` and `stamp()` do. Without the `ots` binary nothing breaks: records are still kept and listed in manifests, capture is unaffected, and the result says `ots not installed: records are not sealed; install opentimestamps-client or set ots: false`.

## What's NOT in mailproof, and why

- **The body and the raw email are never in the record or the trail.** A record is the signed headers, the signature, the archived key and hashes; this keeps other people's mail content out of your trail and out of anything you export. With the local content store on (default) the raw email and attachments are kept beside the trail, outside git, until retention or `forget` removes them (`content.store: false` turns it off). `matchBody` re-checks a body you produce later.
- **No per-record erasure.** Records are durable by design (a git chain); privacy is minimisation plus lawful retention, not deletion.
- **No sending, no IDLE watcher, no OAuth flow, no whole-mailbox recording, no multi-account orchestration.** You hand mailproof raw bytes, or point `sync` at named folders of one mailbox.
- **No acting on a verdict.** `verified` is a statement about the signature, not a decision.

## Threat model summary

- Guaranteed: a record cannot be edited without failing `verify` (signed headers are re-hashed against the archived key); every tamper in findings F6 fails closed; a bad `captured` fails closed.
- Assumed: your trail directory is yours. `captured` is mailproof's own clock; OpenTimestamps (on by default; the stamp job seals batches of records) makes "captured no later than T" provable, up to the cadence plus the sync gap after capture.
- Out of scope: SPF can never be re-checked from stored data (the portable verdict is DKIM only); a sender who never signs cannot be proven.

## The `mailproof` command (M3 step 5, SPEC B11)

`mailproof` (a `bin` of the package, `src/cli/`) is a thin layer over the class: no arguments on a terminal is a menu, otherwise `mailproof <command> [flags]`, each command one library call. Accounts come from one strict JSON config (`$XDG_CONFIG_HOME/mailproof/config.json`, mode 0600 and owned by you or exit 77; unknown keys and plaintext `pass`/`password`/`secret` refused with 64; secret by reference only: `passCommand` | `passFile` (owned by you, mode 0600, else refused) | `accessTokenCommand`; a `backupRemote` URL carrying credentials is refused with 64, use a credential helper or an ssh key); `--account` is required with two or more accounts. Commands: `sync [--folders --sent]` (sync + content sweep + `upgradeStamps` when `ots`), `watch [--interval 30s|5m|1h]` (foreground; backoff; 77 on a refused login), `list`, `show <id> [--raw]`, `verify <id> [--at]`, `replies <messageId>`, `check <id> --profile <file|name> [--parent <messageId>]`, `forget <id...>|--with <address>`, `prune --before <date> [--delete-backup]` (both: dry-run summary, `--yes` required, `--dry-run`), `backup [--out --with-content --push --yes]` (git bundle; `.content.tar` by `tar`; push never forces), `status`, `update [--run]`, `config path|validate|template|add-account`, `help [command]`; `export --with <a,b> [--after --before --out --tar]` (the pair bundle above; default out `./mailproof-bundle-<account>-<UTC yyyymmdd-hhmmss>`; 64 for a bad value or an existing `out`, 75 for a lock or a prune during the read, 1 for nothing selected or too big), `verify-bundle <dir> [--expect <sha256>] [--strict]` (account-free, needs no config; exit 0 ok, **2** a check failed, 64 bad usage; `MAILPROOF_OTS=off` skips the seal check); `mcp` is the stdio MCP server (next section; on a terminal it exits 64). An id is 32 hex or a unique prefix of 8+. `--json`: one document on stdout (`watch`: one line per tick); its strings are data as received (control, C1, bidi and zero-width characters are NOT stripped), so treat them as untrusted; text mode escapes them (`\x1b`, `\u202e`, `\\`) and `show --raw` stays raw bytes. Exit codes: 0 done, 2 a check ran and the answer is no (`verify`, `check`), 64 usage, 75 try later, 77 permission or login refused, 1 other. Library additions with it: `upgradeStamps() => { enabled, upgraded, pending, error? }` and `prune({ ..., dryRun: true })` (same shape, `dryRun: true`, nothing written).

## The MCP server (`mailproof mcp`, M3 step 6, SPEC B12)

`mailproof mcp` is a stdio MCP server (no SDK, no dependency) over the CLI's config: one process, every account, an `account` argument on each account-bound tool (required with two or more accounts; `--account <name>` restricts the server to one). 29 tools named like the methods (parity with the CLI, 2026-11-12): `accounts`, `status`, `list`, `get`, `describe`, `copies`, `counterparties`, `linked`, `verify`, `verifyWith`, `verifyRecord`, `verifyBundle`, `proofParts`, `checkProfile`, `replyFacts`, `matchBody`, `matchFile`, `rawEmail`, `attachment`, `check` (read); `record`, `replyText`, `sync`, `stamp`, `upgradeStamps`, `export`, `backup` (write; `export` and `backup` preview unless `confirm: true`, then write only under `mcp.outputDir` under a plain name; `backup` with `push` contacts the account's `backupRemote`, never forced); `forget`, `prune` (destructive: preview unless `confirm: true`). Not tools: `watch`, `config add-account`, `help`, `mcp` (`status` carries the config check, the version and `updateCommand`). `verifyBundle` takes a `dir` inside `mcp.inputDirs`. `stamp` sends one 32-byte manifest hash to the OpenTimestamps calendars. Register: `claude mcp add mailproof -- mailproof mcp`.

- **Known limit: hints are advisory, not a gate.** Every tool has all four annotations, but Claude Code 2.1.322 ignores them (F30): scope by tool name in the client's allow rules (`mcp__mailproof__list`) or one server per account (`--account`). `confirm: true` on `forget`/`prune`/`export`/`backup` is the only server-side guard. `rawEmail`/`attachment` are read-only yet hand over other people's mail. On shutdown the server waits 5 s for in-flight calls, but a call still blocked in I/O can keep the process alive until its own timeout (measured: a `sync` stuck connecting held it 29.7 s, the 30 s `SYNC_CONNECT_MS`; worst case `SYNC_SOCKET_MS`, 5 min); MCP clients normally kill the child.
- **Bytes.** An email or file goes in as `base64` or an absolute `path` (refused unless inside config `mcp.inputDirs`; default none). `rawEmail`/`attachment` return an embedded blob up to `mcp.maxBinaryBytes` (1 MiB) or `saveTo` a file name in `mcp.outputDir` (default none; never overwrites); `export`'s `out` and `backup`'s `out` are plain names in the same folder.
- **Results** are compact JSON text; over `mcp.maxResponseBytes` (512 KiB) is `ERR_RESPONSE_TOO_LARGE`, never a truncation. Unknown id: `{ "found": false }`.
- **Errors** are `isError` results: `{"error":{"code","message","retryable"}}` with the library's `err.code`, or `ERR_BAD_ARGUMENT`, `ERR_PATH_NOT_ALLOWED`, `ERR_TOO_LARGE`, `ERR_RESPONSE_TOO_LARGE`, `ERR_INTERNAL`; `retryable` for `ERR_TRAIL_LOCKED`, `ERR_SYNC_LOCKED` and transient IMAP codes.
- **`sync`** reads at most 100 messages per folder per call (`maxMessages` lowers it); loop while `complete` is false.
- **Everything derived from an email is untrusted data**; the descriptions and `initialize.instructions` say so. Write and destructive calls are logged one line each to `<state>/mcp.log`.
- The tool list is generated: `src/mcp/tools.js` (annotations, parameters) + `primitives.json`/`@mcp` JSDoc blocks, `npm run build:mcp-tools`.

## Run on a timer (`mailproof-sync`)

`mailproof-sync` (shipped as `bin/mailproof-sync.js`, on `PATH` after `npm i mailproof`) is one `sync` run for cron or a systemd timer. It reads the password from a command, a file or stdin, never from a flag or a plain env value, and prints one JSON line (the sync result, no secret) on stdout and errors on stderr.

```bash
mailproof-sync --trail-dir /var/lib/mailproof --user you@gmail.com \
  --pass-command "pass show mailproof/gmail_pass"      # host imap.gmail.com, folders INBOX, sent on
```

Flags (env fallback `MAILPROOF_<NAME>`): `--trail-dir`, `--trail`, `--host`, `--port`, `--user`, `--folders a,b`, `--sent on|off`, `--pass-command` (split into arguments, run without a shell; first stdout line is the password), `--pass-file` (owned by you, mode 0600, else refused), `--access-token-command` (OAuth2 XOAUTH2). With none of the secret sources, the password is read from stdin. Spaces are stripped only from Google's app-password display shape (four groups of four lowercase letters); any other password is sent as given, minus surrounding whitespace.

Exit codes: `0` finished (a run cut short by a cap also exits 0 with `"complete": false` and no error: the next run continues from the cursor); `75` try later (`ERR_SYNC_LOCKED` or `ERR_TRAIL_LOCKED`, server unreachable, timeout, throttled); `77` login refused; `64` bad usage; `1` anything else.

`~/.config/systemd/user/mailproof-sync.service`:

```ini
[Unit]
Description=mailproof IMAP capture

[Service]
Type=oneshot
ExecStart=/usr/bin/env mailproof-sync --trail-dir %h/mailproof-trails --user you@gmail.com --pass-command "pass show mailproof/gmail_pass"
SuccessExitStatus=75
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=%h/mailproof-trails
ProtectHome=read-only
```

`~/.config/systemd/user/mailproof-sync.timer` (then `systemctl --user enable --now mailproof-sync.timer`):

```ini
[Timer]
OnCalendar=*:0/15
Persistent=true

[Install]
WantedBy=timers.target
```

For a system unit add `User=mailproof`. `ProtectHome=read-only` keeps the `pass` store readable; the trail directory needs `ReadWritePaths` because `ProtectSystem=strict` makes everything else read-only. `SuccessExitStatus=75` keeps an overlapping or temporarily unreachable run from marking the unit failed. Equivalent cron line:

```cron
*/15 * * * * mailproof-sync --trail-dir $HOME/mailproof-trails --user you@gmail.com --pass-command "pass show mailproof/gmail_pass" >> $HOME/mailproof-sync.log 2>&1
```

## Gotchas

- Mail altered in transit or by an export tool fails `matchBody` while `verify` still passes (headers intact); `body_status` says so at capture, with hints when the change can be explained.
- The trail layout is sharded: `records/<id[0:2]>/<id>.json` (+ `.json.ots`), `manifests/<seq>.json` (+ `.json.ots`, the stamp manifests, M4) and `replies/<id[0:2]>/<id>.<slug>.json`, `<id[0:2]>` the first two hex chars of the id. A trail written by 2.2.x or earlier (`records/<id>.json` flat) is not read or converted: every call fails with `code: 'ERR_TRAIL_LAYOUT'` and the trail must be re-created.
- A signature whose key is gone from DNS at capture is stored with `key_error`; it cannot verify.
- A message over an input limit (25 MiB, 10 DKIM signatures, 256 KiB per body line, 500,000 body lines, ...) or one the worker backstop stops is still recorded, but never parsed: `unverified`, `reason: 'over limit: <name>'` (`time` / `memory` / `crash` for the backstop). A worker that cannot start rejects `check()`/`record()` and records nothing. Only `envelope.clientIp`, `clientHelo` and `sender` are read; each is a string or `null`: any other type (a function, a number) is treated as `null`, in a worker and with `worker.size: 0` alike; an `envelope` that is not itself an object counts as no envelope. Limits are in `docs/product/SPEC.md` Part B (Limits).
- `sync` holds a second lock file, `<trailDir>/.<trail>.sync.lock`, for the whole call; it never holds the trail lock across IMAP I/O. A pipe delivery during a backfill waits behind at most one message's commit.
- Writers are serialised per trail by a lock file that also covers separate processes (local filesystems only); a writer that waits longer than `lockTimeoutMs` gets `ERR_TRAIL_LOCKED`. Map it to a retry (Postfix: exit 75).

## Constraints

- Node >= 22.19; pure ESM (`import`, no `require`).
- One trail = one git repo; one writer at a time per trail, across processes too (lock file `<trailDir>/.<trail>.lock`, local filesystems only).
- Trail names match `/^[a-z0-9][a-z0-9_-]{0,63}$/`; record ids are 32 hex characters.
