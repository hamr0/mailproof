### Decision: Pure ESM (0.8.0) — repackage CJS → ESM
**Date**: 2026-05-29
**Status**: Accepted
**Context**: `LIBRARY_CONVENTIONS.md` §1 mandates pure ESM (`"type": "module"`) for every published suite library; mailproof was the last one still on CommonJS (`require`/`module.exports`), the standing open delta after the 0.7.0 types realignment. ESM is also the ecosystem default and what TS consumers expect.
**Decision**: Migrate the whole package to ESM and ship it as **0.8.0**. The bulk was mechanical (a one-shot codemod: `const {a}=require('./m')` → `import {a} from './m.js'`, `module.exports={...}` → `export {...}`, strip redundant `'use strict'`), with the `.js` extension added to every relative specifier in code **and** JSDoc `import('./x.js')` type references (node16 resolution requires it). Three seams were reworked by hand: `parse.js`'s variable-specifier `require('mailparser')` (kept the JSDoc type-cast over a default import), inline `require('node:dns')` in `verifier.js`/`dkim-archive.js` (hoisted to top-level imports), and the lazy `require('./gitrepo')` in `event-store.js` (static import; construction stays lazy). `create.js`'s whole-module captures of `completion`/`crypto` became `import * as`. `poc/pipeline.js` → `poc/pipeline.cjs` so the superseded P0 proof still runs.
**Consequences**: Minor bump (no API surface change — same 59 exports, `create()`/`ingest()`, 12 occasion kinds), but a breaking module-system change for any consumer doing `require('mailproof')`: they must now `import`. 307 tests pass, typecheck 0, `build:types` clean. Removes the last convention delta; P2 (gitdone rebuild) will consume the ESM surface.

### Decision: Git-native storage (events as JSON + per-event git repo)
**Date**: 2026-05-22
**Status**: Accepted
**Context**: mailproof needs a store for event state and an audit record. Options were a database as the source of truth vs. the git ledger as the source of truth.
**Decision**: Git-native. Event state = JSON + a per-event git repo whose hash-chained commits *are* the tamper-evidence. SQL/other consumers project a read-model; they do not replace the ledger.
**Consequences**: Limited ad-hoc query power and per-event repo overhead, but the proof is portable and offline-verifiable, and "the git ledger is the point" stays literally true. (Mirrors gitdone's original JSON+git decision.)

### Decision: Generic workflow only in v1 (sequencing scope)
**Date**: 2026-05-22
**Status**: **Superseded** (2026-05-24) by "Two generic modes: events + lean crypto sign-off"
**Context**: `completion.js` in gitdone mixes a generic ordered/parallel workflow engine with crypto declaration/attestation, strict signing, revoke, and threshold logic. The lift had to choose how much to bring.
**Decision**: Extract only the **workflow subset** — ordered/parallel/mixed steps. Crypto/attestation, strict signing, revoke, and thresholds stay in gitdone as policy on mailproof's hooks.
**Consequences**: Keeps the kernel lean and generic; consumers needing those modes implement them on the hooks. Risk: the workflow/policy seam must be clean enough that gitdone can rebuild its modes on top (proven in P2).

### Decision: Bundled Postfix/sendmail transport
**Date**: 2026-05-22
**Status**: Accepted
**Context**: Outbound email needs a transport. Options were a pluggable third-party provider (SendGrid/SES) vs. a self-hosted MTA lifted from gitdone's `outbound.js`.
**Decision**: Bundle Postfix/sendmail; opendkim signs outbound at the MTA. Not a pluggable third-party mail provider.
**Consequences**: More operator config (Postfix, opendkim, PTR, port 25 — to be documented in OPS.md) but full control, no vendor lock-in, and DKIM signing under the operator's own domain. Third-party providers are NO-GO (PRD §8.10).

### Decision: Email-only core verify/trigger path (with consumer side-effect carve-out)
**Date**: 2026-05-22
**Status**: Accepted
**Context**: Considered keeping a door open for non-email channels (webhooks/SMS) on the trigger or verify side.
**Decision**: Lock the core verify and trigger paths to email. DKIM/DMARC is what provides cold, third-party, offline verification with no pre-shared secret; webhooks (HMAC/mTLS) require a prior relationship and SMS has no real origin verification — neither preserves the "any two parties, no setup" property. Carve-out: consumers may fire their own side-effect notifications (webhook/Slack/SMS) from mailproof's `ingest()` result, carrying **no** mailproof verification guarantee.
**Consequences**: Email is the trust anchor by construction, not a swappable channel — this is the library's identity. Adopters needing a different channel need a different trust anchor (a different library). Integration reach is preserved via the side-effect carve-out. (PRD §8.1.)

### Decision: `receive.js` is not lifted — primitives + `createReceiver()` hooks
**Date**: 2026-05-22
**Status**: Accepted
**Context**: gitdone's `receive.js` orchestrates the four pillars, but it's tangled with gitdone's config singleton and crypto branches.
**Decision**: Do not lift the orchestrator. mailproof exposes the four pillars as primitives plus an optional `createReceiver()` with policy hooks; each consumer writes its own thin glue.

### Decision: Accept-with-flag (commit every reply, gate the transition)
**Date**: 2026-05-22
**Status**: Accepted
**Context**: How to treat replies that fail routing/trust (wrong participant, unverified DKIM, out-of-order).
**Decision**: Commit *every* inbound reply to the ledger as an audit record; a separate `counted` flag records whether it advanced state. Routing and trust gate the state transition, never the commit.
**Consequences**: Complete, tamper-evident audit trail including rejected attempts (POC: 8 commits, 2 counted). The ledger answers "what was received" independently of "what counted."

### Decision: Config injection by bound per-pillar factories (no config singleton)
**Date**: 2026-05-23
**Status**: Accepted
**Context**: gitdone modules read a `config` singleton (`config.dataDir`, …) evaluated from `process.env.GITDONE_*` at `require()` time, with gitdone-specific defaults baked in (`git-done.com`, `/var/lib/gitdone`). P1 had already decided to "replace the config singleton with injected config" (DESIGN P1) for three reasons: a *library* can't assume the consumer's env-var names, paths, or domain; a load-time singleton is hidden coupling (gitdone's own tests must `delete require.cache` to retest it); and one-singleton-per-process blocks two stores with different `dataDir`s. `outbound.js` (module 4) already injects config **per call** (`binary`, `domain`, `footer`). The open question for the storage pillar was the *form* of injection: per-call vs. a bound factory.
**Decision**: Inject **fixed-per-deployment** config (`dataDir`) via a **bound factory per pillar** — `createEventStore({ dataDir })`, `createGitrepo({ dataDir })`, etc. — each naming the value once and returning the bound primitives. `create({ dataDir, domain, sendmailBin, otsBin? })` composes these factories and remains the single runtime source of truth. Config that legitimately **varies per call** (outbound's `domain`/`footer`, which differ per message) stays per-call. The discriminator is the nature of the value, not uniformity of style.
**Consequences**: Banning the singleton did not remove the single source of truth — it moved it from *implicit* (ambient env, read at import, settable from anywhere) to *explicit* (the `create`/factory call). The factory **preserves** that single explicit binding point; per-call injection of a fixed value would re-fragment `dataDir` across every call site (split-brain risk) — so the factory is the consistent finish to the ban, not a new preference. Trade-off: a mild surface asymmetry (storage = factory, outbound = per-call), justified by the fixed-vs-varying distinction. Simplest at the call site, one source of truth — the project's standing tie-breaker.

### Decision: Two generic modes — events + lean crypto sign-off (supersedes "generic workflow only")
**Date**: 2026-05-24
**Status**: Accepted
**Context**: The original lift scoped mailproof to *generic workflow only* and put all of gitdone's crypto declaration/attestation in the NO-GO table (§8.2). A design conversation reframed mailproof's identity: gitdone's two proven shapes of DKIM-verified multi-party coordination — **events** (named participants, ordered steps) and **attestation/sign-off** (verified signers toward a goal) — are both *generic mechanisms*, not domain policy. The goal became "publish gitdone's engine as a public library" ("same like gitdone but public"), with gitdone-the-product keeping only its web/branding/hosting wrapper. The risk was re-importing completion.js's heavy tail (strict signing, revoke, three dedup variants, attestor_progress, PII redaction — ~500 of its 733 lines) and bloating the kernel.
**Decision**: mailproof offers **two generic coordination modes** on the shared DKIM-verified-email + notary substrate (PRD §1, §4.2): **events** (`type:"workflow"`, the m6 engine) and **crypto sign-off** (`type:"crypto"`). Crypto is **one parameterized engine, not three modes**: `signers` (explicit email list — manually added — *or* open via a shared `attest+{id}@`-style address), `threshold` (1 = single-signer declaration; N = count-to-goal), and an optional single `requiredDocHash` (the "email + doc" two-layer, via the notary). A sign-off counts iff DKIM-verified, sender ∈ signers (or any, if open), a *distinct* sender not already counted, and (if set) the doc hash matches; complete at distinct-count ≥ threshold. **The "link" is a shared email address, NOT a web link/app/webhook** — discovery may be a shared address, but the signing act and its verification are always DKIM email.
**Consequences**: **Lean by exclusion** — explicitly OUT (gitdone policy, §8.2–8.4): `revoke`, `latest`/`accumulating` dedup (distinct-only in core), multi-doc strict manifests + `attach` channel, attestor-PII redaction, magic-link/web flow, branding. Estimated ~100–120 lines vs. completion.js's ~500. **No rework**: the m6 events engine is unchanged; crypto is an *additive* second engine (next module, "m6.7"), and m7's `create()/ingest()` routes by `type`. Identity widens from "sharp primitive" to "headless gitdone" — recorded here as a *deliberate* reversal, not drift. Trade-off: a broader API surface and a fuzzier one-line pitch, accepted for the much higher reuse value of shipping both proven mechanisms. (PRD §1, §4.2, §8.2–8.4, §8.12; supersedes "Generic workflow only in v1".)

### Decision: Crypto sign-off engine (m6.7) — three boundary forks resolved
**Date**: 2026-05-24
**Status**: Accepted
**Context**: Implementing the lean crypto engine (above) surfaced three forks the two-mode decision didn't pin, raised before coding (per the standing "agree the boundary first" rule): (1) is the verified-trust gate hardcoded or a per-event knob; (2) does gitdone's initiator self-reply exclusion survive into the unified engine; (3) does m6.7 also add the `attest+{id}@` router tag, or just the engine.
**Decision**: (1) **Trust hardcoded to `verified`, no per-event `minTrust`** — crypto is the high-assurance mode and letting a forwarded/authorized reply stand as a signature is a footgun; graded trust stays a workflow-only feature (per-step `minTrust`). (2) **Keep the initiator-exclusion in crypto** (`initiator_self_reply`): the initiator may reply and is committed for audit, but their reply never counts as a verification (anti-self-dealing — you can't be both orchestrator and verifier). This diverges from my "drop it" recommendation on the user's explicit call. **Events differ** — there the initiator *may* be a counted participant (m6 unchanged). (3) **Pure engine only**, mirroring how m6 landed: `src/crypto.js` + unit tests + SPEC §3.1/§4 crypto shape; the net-new `attest+{id}@` router tag and SPEC §2 promotion **defer to m7b assembly**, where the route is exercised end-to-end.
**Consequences**: The engine stays pure (no I/O, no crypto): sender-identity resolution is the orchestrator's, passed as precomputed `signer_match` / `is_initiator` booleans — the same boundary as workflow's `participant_match`, so plaintext never reaches the engine or ledger (SPEC §6). ~150 lines, distinct-count-to-threshold only; gitdone's `dedup`/`revoked_senders`/`reference_docs`/`mode` are inert if present (a regression test proves it). Trade-off of (1): a consumer wanting weaker-than-verified sign-off must layer it on the hooks, not the kernel — accepted, since that would dilute the mode's guarantee. (PRD §4.2; SPEC §3.1; CHANGELOG m6.7.)

### Decision: Document notary in scope (auto-hash + `verifyDocument`); doc-as-login is NO-GO
**Date**: 2026-05-24
**Status**: Accepted
**Context**: A design conversation explored using attached documents as a verification layer. Ideas ranged across a per-step hash *gate*, a "claim-check" retrieval credential ("send me a doc we exchanged + your email to unlock X"), and even a login / second factor (magic-link + doc). The question was how much, if any, belongs in the kernel, and whether it collides with the §8.3 strict-signing NO-GO. The user explicitly asked to push back on bloat and admitted no concrete threat model — "I just thought it's neat."
**Decision**: The kernel gains a **minimal document notary**, distinct from gitdone's strict-signing: (1) **mandatory** SHA-256 hashing of *every* inbound attachment into its commit (hashing is always on; whether to *use* a doc as a verification layer is the consumer's choice), and (2) a read-only `verifyDocument(doc)` lookup returning the matching commit(s) with trust/sender/counted info. The document is framed as a **proof-of-participation receipt, not a secret** — the DKIM-verified sender is the trust factor; the doc adds tamper-evident binding/context only. **Deferred** (not NO-GO, built when a consumer needs them): outbound-attachment hashing, `listDocuments`, retrieval-gating. **NO-GO**: document-as-login / second factor (PRD §8.8) — a doc over email is a weak, clunky factor (same inbox; worse than TOTP/passkeys) and the verified sender is already the factor; mailproof is not an auth provider.
**Consequences**: Distinct from §8.3 — strict-signing (pre-registered `reference_docs` manifests, per-attestor progress, completion-gating) stays gitdone policy; the notary only *records and verifies*, it never gates workflow completion, so the completion engine (m6) is untouched by this. Delivers mailproof's "docs hashing, verifiable later" mission with two small additions (m6.5: auto-hash + `verifyDocument`) on the existing ledger, which already stores `attachments[]`. Enumeration of acceptable docs is **not** a leak (SHA-256 is preimage-resistant — a hash list can't produce a file); the real weak point is possession-secrecy, which is why the receipt framing (not password) is the honest one. Risk: scope pressure to grow the deferred items or revive login — guarded by §8.8 and this entry. (PRD §4.1.)

### Decision: git ledger uses the `git` binary via child_process, not `simple-git`
**Date**: 2026-05-23
**Status**: Accepted
**Context**: gitdone's `gitrepo.js` uses `simple-git@^3.20.0`. Lifting it into mailproof would add the **first external runtime dependency**, so AGENT_RULES requires running the External Dependency Checklist first. Audit of the module showed `simple-git` is used for exactly five git operations (`init`, `config`, `add`, `commit`, `status`); `listCommits` reads the filesystem, never `git log`. The two behaviors actually consumed are the commit SHA (`rev-parse HEAD`) and staged-file detection for the byte-strict no-op check in `syncEventJson` (`diff --cached --name-only`).
**Decision**: Do **not** add `simple-git`. Lift `gitrepo` onto the stdlib `git` binary via `child_process.execFile`, through a ~6-line `git(cwd, args)` helper. Note that `simple-git` is itself a thin wrapper that spawns the same `git` binary — it adds output-parsing convenience, not capability or portability; both approaches require `git` installed.
**Consequences**: **Necessity gate fails** for `simple-git` — the five ops are well under the AGENT_RULES <100-line stdlib bar. Zero runtime deps so far, preserving the ≤3 budget for `mailauth` + `mailparser`, which are security-critical (DKIM / untrusted-MIME parsing) and genuinely *require* vetted libraries. Consistent with `outbound`'s zero-dep `sendmail` shell-out and DESIGN's "stdlib + git binary only" P0 baseline. Cost: ~2 commands of hand-parsed git output (`rev-parse`, `diff --cached`), verified against real git by the lifted `gitrepo` characterization tests. The four simple-git conveniences we forgo (empty-commit guard, error surfacing, identity ordering, `index.lock` retries) are handled explicitly — the lock case by m5a's per-event `withEventMutex`.

### Decision: First external deps — `mailauth` + `mailparser` accepted (m7a)
**Date**: 2026-05-26
**Status**: Accepted
**Context**: m7a lifts the inbound decoder (DKIM/DMARC/ARC authentication + MIME parsing), which mailproof had so far avoided — every prior module ran on stdlib + the `git` binary (zero runtime deps). This is the point the ≤3-dep budget gets spent. The AGENT_RULES External Dependency Checklist had to clear before installing. A second finding: the stash labelled m7a a `verify.js` lift, but reading the source showed `verify.js` is gitdone's `verify+{id}@` *endpoint* (forwarded-email report + reverify-against-archived-PEM); the actual inbound authenticate+parse core lives in `bin/receive.js` (the orchestrator, not lifted).
**Decision**: Add **`mailauth`** (DKIM/DMARC/ARC) and **`mailparser`** (MIME) as the first 2 runtime deps. Checklist verdict: **Necessity** — DKIM/MIME of hostile input is thousands of lines and security-critical, so a vetted library is *required* (rolling our own is the forbidden "clever" move); **Maintained/Established** — both by Andris Reinman (Nodemailer author), actively published, the de-facto Node implementations; **Lightweight** — moderate transitive trees (undici, iconv-lite, tldts…), accepted as the *irreducible* cost of correct mail handling, not incidental bloat, and the transitive deps are themselves first-tier; **no new supply-chain surface** — they are the same two packages gitdone already ships. Extract the core as `src/parse.js` (`authenticateMessage` + `parseMessage`), **not** a `verify.js` lift; gitdone's `verify+@` endpoint, DSN bounce handling, and durable dkim-archive reverify are **deferred** to later modules.
**Consequences**: Runtime deps 0 → 2, within the ≤3 budget (the git ledger still uses the `git` binary, not `simple-git`, per 2026-05-23). `authenticateMessage` pins `trustReceived: false` as the one documented, safe call into mailauth (forged `Received`/`Authentication-Results` headers are the obvious attack); its `resolver` injection keeps tests offline and leaves room for the future verify+@ endpoint to re-check against an archived key. `parseMessage` completes the notary **capture** half (deferred from m6.5) by auto-hashing every attachment through `hashDocument` — one fingerprint format kernel-wide. Trade-off: the install footprint grows, accepted because correctness in a security-critical domain outranks a smaller `node_modules`. (CHANGELOG m7a; supersedes the stash's "verify.js authenticate core" label.)

### Decision: Privacy/erasure stance — durability-first; per-record RTBF is NO-GO
**Date**: 2026-05-27
**Status**: Accepted
**Context**: Before m7b freezes the commit format, the question arose whether to bake in a right-to-be-forgotten path — specifically, letting an event participant self-revoke/erase their own ledger records by default. mailproof already minimizes (SPEC §6: no plaintext sender/subject/body/Message-ID; only a salted `sender_hash` + plaintext `sender_domain`). The salt is the only link from hash→person; today it is **public and committed in-chain** (`event-store` generates it; `gitrepo.syncEventJson` mirrors the whole `event.json` — salt included — into the immutable per-event repo). So records are pseudonymous, not anonymous, and not erasable without breaking the chain.
**Decision**: **Durability-first.** mailproof's value is a tamper-evident, non-repudiable, offline-verifiable multi-party proof — all three of which per-record erasure attacks (deleting a commit rewrites every descendant SHA; erasing a counted reply turns "3 of 3 signed" into "2 of 3"; the salt must travel in the repo for "git clone = the proof"). Therefore: (1) privacy = data minimization (already a core invariant) + the "receipt, not secret" framing (the DKIM-verified sender is the trust factor; the hash only binds); (2) per-record self-revoke / erasure is a **NO-GO** (PRD §8.16) — it contradicts non-repudiation and tamper-evidence, and GDPR's erasure right carves out the establishment/exercise/defence of legal claims and legal obligations, under which a contractual sign-off record plausibly falls (not legal advice); (3) the ONLY erasure lever is coarse and opt-in: destroying an **entire event** (the consumer deletes `event.json` + the repo) also destroys that event's salt, making any residual exported hashes unlinkable — whole-event crypto-shredding falls out of event deletion, **nothing new to build**. The public in-chain per-event salt stays, chosen over a destroyable out-of-chain salt because verifiability ↔ forgettability are the same dial and public offline verification (the `verify+@` proof-of-participation) is the product.
**Consequences**: No new erasure subsystem; m7b's commit format is unaffected. The privacy story is honest: minimized + pseudonymous + durable by design — not anonymous or per-record forgettable. **Rejected alternatives**, recorded so they aren't relitigated: (a) *forgettability-capable* — a destroyable, out-of-chain, per-participant salt enabling crypto-shred RTBF, buildable later if a consumer's legal posture demands it, at the cost of public offline verification; (b) *tombstone/logical-delete* — append-only redaction commits that hide records from projections but leave the hash + public salt intact, so not true anonymization. (PRD §8.16; SPEC §6.)

### Decision: Email triggers — occasions are kernel (+ neutral templates), bodies are policy; roadmap m7c verify → m7d triggers
**Date**: 2026-05-27
**Status**: Accepted
**Context**: After the m7b assembly + m7c-1 landed, the user flagged that gitdone's email triggers are rich (`notifications.js`: `notifyWorkflowParticipants` incl. reminder mode, `notifyEventCompletion` with embedded receipts, `notifyOrganiserOfActivation`, `notifyInitiatorOfSigningProgress`, `notifyOrganiserOfStepProgress`, `notifyProofAnchored`, `notifyDeclarationSigner`; plus `sweep.js` for reminders/deadlines/archive and `dsn.js` for bounces) and that mailproof's Commit-C trigger layer emits only three (`advance`/`ack`/`completion`). The tension: §8.6 makes branded email *bodies* a NO-GO, but the north-star acceptance test ([[mailproof-rebuilds-gitdone-acceptance-test]]) requires a consumer to be able to rebuild gitdone — so the full set of trigger *occasions* must be expressible without re-deriving kernel state.
**Decision**: Split the trigger pillar on **occasion vs body**. *Occasions* (the events that warrant an email — derivable from a state transition, a timer, or an inbound bounce) are **mechanism**: mailproof emits every occasion it can derive, each as a `kind` with a **simple neutral default template**, all overridable through the single `composeNotification(ctx)` hook keyed by `kind`. *Bodies/branding/prose* stay **policy** (§8.6 intact). This requires absorbing three deferred subsystems into the kernel: **`sweep()`** (time-driven `reminder`/`overdue`/`archived`), **`dsn.js`** (inbound bounce → `bounce`), and small **activation** + **edit-renotify** hooks; plus richer `completion` ctx (the counted commits/receipts, so a consumer can embed proof without mailproof owning the body) and `proof_anchored` (rides on OTS verify). The Commit-C `composeNotification`/`deliver()` seam already supports this — it is extended with `kind`s, not reworked. **Stays policy:** gitdone's strict-attach "docs needed" nudge and signing-progress UX prose.
**Consequences**: Roadmap ordering set (user's call): finish **m7c** (the verification surface — `verify+`/`reverify`/OTS-verify/e2e) FIRST, because the gitdone reconverge (P2) hard-depends on offline verifiability, THEN a dedicated **m7d** triggers milestone that absorbs all kernel-derivable occasions + neutral templates. Reaffirms §8.6 (no branding in the kernel) while widening the trigger pillar from "fire the next email" to "emit every occasion, neutrally templated." `sweep()` and `dsn` graduate from "deferred" to "scheduled (m7d)". (CHANGELOG m7c-1; PRD status/roadmap; supersedes the stash's "DEFER sweep()/DSN" line — they are now roadmap, not dropped.)

### Decision: OTS-proof verification = `ots upgrade` + `ots info`, never `ots verify`
**Date**: 2026-05-27
**Status**: Accepted
**Context**: m7c-4 (the last verify slice) needed a way to confirm a committed `.ots` proof is genuinely Bitcoin-anchored, not just calendar-pending. The obvious primitive is `ots verify`. But reading gitdone's working wrapper — which I initially missed in `app/src/ots.js` (stamp-only) and the user pointed to in `app/bin/ots-upgrade.js` — showed gitdone deliberately avoids `ots verify`: it queries the calendar servers *live*, so it reports "verified" for a proof whose attestation hasn't actually been folded into the file. If the calendars died, that proof would be unverifiable offline despite having "passed".
**Decision**: Port gitdone's design as the kernel primitive: `createOts().upgradeProof(abs)` runs `ots upgrade` in place and treats the proof file's **sha256 changing** as the authoritative "now anchored in Bitcoin" signal (the calendar attestation was merged into the file — now offline-verifiable forever); `readBlockHeight(abs)` reads the anchored block via `ots info` (parses the binary proof **locally, no network**); and the pure `parseOtsBlockHeight` (re-exported) is the testable output parser. `ots upgrade`'s non-zero exit on a still-pending proof is modelled as `{ pending: true }`, **not** an error (accept-with-flag). We never call `ots verify`.
**Consequences**: The trust anchor is durable and offline (the upgraded `.ots` carries the Bitcoin proof), matching mailproof's "git clone = the proof" thesis — not a live calendar query. Kernel/policy split (consistent with the triggers-occasions entry above): the **primitive** is kernel (`createOts`); the **scheduler** that walks an event's proofs, records `ots_anchored` into the ledger, and emits the `proof_anchored` occasion is policy/glue, deferred to **m7d** (it's gitdone's `processRepo`/`run` cron, not the wrapper). Testability: the pure parser is unit-tested across the opentimestamps-client output shapes; the subprocess wrappers are integration-tested for the binary-missing path + a real-`ots` non-proof smoke test (deterministic, no network); the fully-confirmed-proof path stays deployment-verified (needs ~1h of Bitcoin confirmations). With m7c-4 the 9-point [[mailproof-rebuilds-gitdone-acceptance-test]] checklist is fully covered. (CHANGELOG m7c-4; SPEC §4 tamper-evidence.)

### Decision: pending-activation TTL/reminder is consumer policy, not a kernel occasion (m7d-2)
**Date**: 2026-05-27
**Status**: Accepted
**Context**: m7d-1 deferred two of gitdone `sweep.js`'s passes to m7d-2: the never-activated TTL-DELETE (purge events created but never activated, after ~72h) and the pending-activation about-to-expire REMINDER. Implementing m7d-2 (the activation lifecycle) forced the boundary question the deferral left open: are these kernel occasions?
**Decision**: **No — both are consumer policy.** (1) The TTL-delete is destructive and the privacy decision (durability-first; 2026-05-27) already names whole-event deletion as the consumer's only erasure lever — the kernel must not auto-delete an audit record. (2) The about-to-expire reminder presupposes a SELF-SERVICE activation UX (the organiser must take an action — gitdone's magic-link click — or the event expires), which mailproof deliberately dropped when it trimmed gitdone-web's magic-link activation (m5a). In mailproof, activation is a programmatic `activateEvent()` call; a draft sitting un-activated is the consumer's intent, not a countdown. So m7d-2 ships only the two occasions that ARE kernel-derivable from a real transition: `activation` (first `activateEvent` → kickoff to initially-eligible participants/signers) and `reassigned` (`editEvent` moves a participant onto a currently-eligible step). ### Decision: M1 IMAP capture (`sync`) design

**Status**: Accepted (owner: hamr0)
**Context**: PRD §7 M2 was "Reading replies": strip quoted text, then pluggable interpreters (strict keyword, calendar reply, an LLM hook) and a decision record. The fork: how much of "what did the reply mean" mailproof owns. Options: (a) keep the interpreters in mailproof; (b) mailproof returns the new text with proof and the consumer interprets it.
**Decision**: (b). M2 becomes "Reply text": given a recorded reply and its raw bytes, return only the text the sender newly wrote plus proof it came from that signed email (text from the body, body matches `bh=`, signature is the sender domain's). Stripping is deterministic and versioned (`mailproof-quote/1`), so anyone re-runs it byte for byte. Dropped from mailproof: the keyword interpreter, the calendar-reply interpreter and the LLM hook. Signatures are not stripped, only quoted history. Limits are flagged in the output: unproven where the body does not verify (Outlook/Exchange copies), `quote: not-found` returns the whole body, `quote: inline` is flagged and not merged. A small `reply-text` record (hash, byte count, stripper version, quote flag, `body_status`, time; no text, no body, no subject) is committed per extraction. The POC on real replies from real clients is still required. M2 starts with ledger item C2.
**Rationale**: keyword lists are guardrail policy and do not scale (synonyms, emoji, every language multiplies them); the consumer's LLM reads free text better; PRD §10 already says mailproof produces a verdict and acting on it is the consumer's job. Signature detection is another fragile heuristic, and the signature is text the sender did write. The narrow claim stays provable. Calendar replies are not dropped as a concept; if needed they belong with M4.
**Ledger revalidation (same day)**: the fix-ledger was rechecked on evidence (something that happened), not edge cases or feelings. Kept: C2 (measured, [F18](findings.md)). Dropped as not observed: the `trailHead` damaged-`.git` guard (reproducible only by hand-placing an empty `.git` inside a parent repo), the per-call IMAP list deadline (needs a hostile server), git-error-as-no-commits (never observed), I2 transient kill made permanent (never tripped on real mail), and the Google app-password NBSP (no evidence Google emits it). One stale comment fixed (`SYNC_MAX_MS`).
**Consequences**: PRD §7 M2 and §10 updated. The decision record in the old M2 text is replaced by the reply-text record. Wire format goes to SPEC Part B when M2 is built.

### Decision: Trail index: better-sqlite3 as the 4th runtime dependency
**Date**: 2026-11-07
**Status**: Accepted (owner: hamr0)
**Context**: [F18](findings.md) measured `list()` and `copies()` as a linear full read (about 65 to 110 us per record: 1.2 s at 10k records, 10 to 30 s at 100k), and M3 needs a Message-ID lookup. [F19](findings.md) ran a POC of the options, all checked against the full-read answers. Options: (A) `node:sqlite`; (B) `better-sqlite3`; (C) keep the full read; (D) `git log --grep` for `list`; (E) a stdlib JSON-lines sidecar loaded into Maps.
**Decision**: B, `better-sqlite3` `^13.0.3`, as the 4th runtime dependency, behind one module (`src/proof/index-db.js`). A rebuildable cache `<trailDir>/.<trail>.index.sqlite` beside the lock file, outside git, keyed on the trail's git HEAD (catch-up from `git diff`, else rebuild), written under the trail lock. If the addon cannot load, `list`/`copies` reject `ERR_INDEX_UNAVAILABLE`; no fallback to the full read. E was not pursued (never built end to end).
**Rationale**: the only measured option that is flat from 1k to 100k records (tens of microseconds per query, 4 ms open, rebuild 36 s at 100k) and answers `copies` and Message-ID lookups. A: the `ExperimentalWarning` cannot be silenced from library code, Node 22.19 was not run, the SQLite inside varies by Node build, and it is 1.7x slower. D: wrong when capture order differs from commit order, `list` only. C: linear. The index is a cache: proof (`record`, `get`, `verify`, `matchBody`, `matchFile`, `sync` capture) never loads it, and the JSON records stay the truth.
**Consequences**: The ceiling of 3 runtime dependencies is lifted by owner decision; a further dependency still needs the AGENT_RULES checklist. `better-sqlite3` is a native addon: 13.x ships prebuilt binaries for 8 platforms (darwin x64/arm64, linux x64/arm64 glibc and musl, win32 x64/arm64) in the npm tarball and has no install script; other platforms get `ERR_INDEX_UNAVAILABLE` from `list`/`copies` only. `list`/`copies` can now throw (the addon, or `ERR_TRAIL_LOCKED` while an index update waits for a writer). Equal `captured` now order by ascending id. Whoever can write the index file can change `list`/`copies`, never `get`/`verify`. SPEC B5.

### Decision: M2 stripper after the POC: `trailing` flag, own decoding, partial is unproven
**Date**: 2026-11-07
**Status**: Accepted (owner: hamr0)
**Context**: [F20](findings.md): the owner reviewed all 23 POC extractions and marked them correct. In 9 of 23 (all Thunderbird) unquoted text follows the quote (a signature below it, or bottom-posted text), and cutting at the first boundary drops it. Two further forks came up in building M2.
**Decision**: (i) `mailproof-quote/1` keeps returning the text above the first boundary and adds `trailing: true` when non-empty unquoted text follows the quoted part (not for `inline`, not for `not-found`). Options: (a) a flag; (b) return the below-quote text separately; (c) drop it silently. **a** chosen: a separate below-text would be a second thing to decode, hash and interpret, and merging it into the text would send quoted-looking content into the answer; silent drop is the trap this module exists to remove. (ii) The source text is the first `text/plain` part decoded by mailproof's own stdlib code (transfer encoding, then `TextDecoder`), not mailparser's conversion, so the hash depends only on the bytes and the stripper version; a message with no usable `text/plain` part gets no extraction (`source: 'html-only'`, empty text, flagged unproven). (iii) `partial` body status (an `l=` signed prefix) counts as unproven in v1: mapping the signed canonical byte count onto the decoded text is not proven; it fails closed and is revisited with evidence. Only `matched` is proven.
**Consequences**: PRD §7 M2 honest limits gain item 4 and a precise item 1. Wire format: [SPEC B6](SPEC.md). A later rule change is a new stripper version (`mailproof-quote/2`), never an edit of `/1`.

### Decision: M3 scope: one trail per owned account, local content store, prune-before-date, CLI + stdlib MCP
**Date**: 2026-11-08
**Status**: Accepted (owner: hamr0); specified, not built
**Context**: PRD §7 M3 was "goals only". The owner interviewed it into a spec. Forks: how trails map to people and accounts; how to organise a trail for retrieval; whether threading is a feature; whether to keep storing no body; what retention and deletion mailproof offers; which interfaces ship and with what dependencies.
**Decision**:
1. **Goal.** One substrate for three use cases (agent approvals, request/reply on record, a record of agreement or communication between two people incl. agent audit replay). mailproof records everything in and out; use cases are read-side primitives and policies. Multi-party stays in gitdone.
2. **Trail per owned account.** Options: (a) one trail per counterparty; (b) one trail per owned account; (c) one trail for everything. **b.** Business and personal accounts are never merged; aliases and plus-addresses of one mailbox share a trail. (a) multiplies repos and a mail with several parties has no single home; (c) mixes accounts that must stay apart.
3. **Counterparty = one exact address.** No grouping. DKIM proves a domain or an address, not a person; merging `bob@gmail.com` and `bob@company.com` would assert an identity we cannot prove.
4. **Trail organisation unchanged** (one commit per copy, linear, flat `records/`). Options: a branch or folder per counterparty. Rejected: a CC'd mail needs two homes, creating them on receive runs inside the lock, threads cross structures. Retrieval uses the rebuildable SQLite index (SPEC B5), extended with participants and thread links. Each record proves itself; git gives append-only history.
5. **Threading is not a core feature.** Report "look linked" with graded strength (signed / unsigned / none), never "definitely the chain". Unsigned links are real (Microsoft, F11), so a binary answer would be wrong.
6. **Local content store, on by default; reverses "never store the body".** Raw email keyed by record id, attachments keyed by sha256, beside the trail, outside git, outside the SQLite index, write-once, separate opt-outs for content and attachments. Options: keep proof-only (status quo); store in the index; store in git. Status quo keeps every primitive dependent on a mailbox that may delete the mail. The index is a disposable cache and content is the only copy once the mailbox deletes it. In git, every export or shared proof would carry content. The old rule came from gitdone/signedreply.com VPS storage limits; mailproof is a local setup. Stored content makes every primitive work offline and adds a verification layer: the stored bytes self-verify against the record id.
7. **Retention.** Content: days per account, default 730, auto-deleted. Proof records: permanent. `forget` is early content deletion. Options: expire proofs too (rejected: proof is what remains when everything else is gone); no expiry (rejected: unbounded storage of other people's mail). After content is gone, headers re-verify; `body_status` is a fact that cannot be re-checked; anyone producing the raw email or attachment gets full re-verification.
8. **Prune before date**, off by default, explicit command. Only a prefix of history, never a middle range (that is tampering), no rotation by period. Procedure: lock, prune-notice first commit, replay kept commits with original message/author/date, re-verify kept records, build aside and swap, keep `<trail>.pre-prune-<date>`. Options considered: in-place rewrite (a failure damages the trail); date-range delete (tampering); per-record erasure (stays out, PRD §10). Kept proofs, keys, stamps and content stay byte-identical; only commit ids after the cutoff change.
9. **Trust profiles** as a read-side policy primitive (allowed senders, required checks, body level, link strength); re-evaluable later on the same record. **Graded proof per part:** email and each attachment separately.
10. **Interfaces.** Library; one `mailproof` CLI (no arguments = readline menu, same actions as subcommands; `export` needs M6's bundle); JSON config per user (JSON so no dependency); an MCP server in the same package. MCP written on the stdlib (stdio JSON-RPC), no SDK. Options: the MCP SDK (a new dependency, checklist and owner decision needed); a separate package. Stdlib first, proven by a POC against a real client (Claude Code); switch to the SDK only if the protocol work proves larger. MCP starts read-only; no forget, export or send without a human gate. CLI help, MCP descriptions and `primitives.json` come from the same JSDoc. No new runtime dependency for M3.
11. **Build order:** content store + retention + forget; trust profiles + counterparty view + link grades; prune; CLI + config + menu; MCP after its POC. POC first for the stdlib MCP server and the prune replay. The bareguard approval becomes a recipe on top.
12. **Left open:** sending the request email (PRD §12 Q6), the bareguard recipe and its trust bar, MCP write tools and their human gate, the `watch` mechanism (interval vs IDLE), and whether a minimal pair/thread export ships before M6.
**Consequences**: Proof records now sit beside a local store of other people's mail by default, so the privacy note in the usage guide covers both (what is stored today vs planned). PRD §4, §7 M3, §10 and §12 updated; the M6 "whole-inbox" line is reconciled (INBOX + Sent already covers in/out; all-folders is a config option). Out of scope stays: per-record proof erasure, deleting a middle range, rotation by period, a git per counterparty. A shared or exported proof carries no content. The stored raw email is a second copy of data the mailbox also holds. Prune rewrites commit ids after the cutoff, so anything that cites a commit id must cite the record id instead. No evidence for any mechanism yet (no findings F-entries): the prune replay and stdlib MCP are unproven until their POCs.

### Decision: M3 approvals: mailproof never sends; supplies a flat fact bundle; bareguard decides
**Date**: 2026-11-09
**Status**: Accepted (owner: hamr0); specified, not built
**Context**: Second M3 interview round. Open items: how the request email gets sent (PRD §12 Q6), who judges a reply, what shape the result takes for bareguard's `humanChannel`, and how Microsoft senders fit (F10, F11).
**Decision**:
1. **mailproof never sends.** Options: (a) send through the user's own mailbox over SMTP; (b) bring-your-own Message-ID, the initiator sends; (c) mailproof builds and sends the email. **b.** The initiator sends with its own tools from the user's own account, ideally setting its own Message-ID; mailproof records the request from Sent and the reply from Inbox. (a) adds sending code, credentials and probably a dependency; (c) also puts mailproof in the middle of what is asked. b keeps mailproof a silent shadow and the "no third-party sending provider" rule intact. §12 Q6 is answered.
2. **mailproof supplies, consumers decide.** Options: mailproof decides ("approved" yes/no); consumer decides. **Consumer.** mailproof never interprets or filters for a consumer. A later read primitive `replyFacts({ messageId })` (name proposed) returns everything mailproof knows about the reply, or null. The trust profile stays separate and optional. Deciding inside mailproof would bake one consumer's policy into the library.
3. **Bundle shape.** Options: nested typed object; flat JSON with string values. **Flat strings**, each flag from a closed set, claimed and proven as sibling keys (`from` vs `fromDkimAligned`; `link`; `bodyProven`). Agreed with bareguard's session: its rubric reads only own top-level keys, compares strings exactly, and has no rule for booleans or nested objects. Multi-value fields are one string with a separator fixed at build.
   **Addresses are supplied lower-cased** (`from`, `to`, `cc`, any domain field; stated in the contract), with the address as written as a sibling (`fromRaw`, and `toRaw`/`ccRaw` if convenient). Options: raw only (bareguard's exact, case-sensitive `in` rule would deny a genuine `Ana@Company.com`); normalised only (hides what was written). Both: domains are case-insensitive and local parts are in practice, and the raw value keeps nothing hidden. Rubric values for `from` are written lower-case.
4. **`firstLine` is exactly defined** (PRD §7 M3), because a consumer compares it byte for byte: first non-empty line of the new reply text after `String.prototype.trim`, no case folding or normalisation, `""` if none. Text and `firstLine` are supplied even when unproven; `bodyProven` says so.
5. **Reference recipe lives on bareguard's side** (owner picked it in bareguard's session): reply with an exact approval word as the first line; rubric uses bareguard's `in` rule on `firstLine`, `from`, `fromDkimAligned`, `bodyProven`, `link`; anything not green is not approved; one answer per ask; proof reference in the audit via `reason` or `gate.annotate`. mailproof documents the adapter; it adds no behaviour.
6. **Microsoft is a documented limit.** Options: a per-question tag in the subject or quoted body (works, Microsoft signs Subject); a tag recorded in git (proves only what we sent, not what their signed reply answers); known limitation. **Known limitation.** Microsoft senders get `link` = `unsigned`; mail received at Outlook/Exchange is always `unproven` (receive approvals elsewhere). A strict rubric rejects Microsoft approvers; a relaxed one accepts them and risks a replayed old approval from the same sender. That trade belongs to the bareguard user. The owner preferred a clear limit to a tag scheme.
7. **Evidence task, not done:** sample one reply each from Yahoo, iCloud, Proton and Fastmail to see whether they sign In-Reply-To/References (per-provider config; only Gmail and Microsoft measured).
**Consequences**: M3's Open list loses "sending" and "the bareguard recipe"; it keeps MCP write tools, the `watch` mechanism, export timing and the provider sampling. `replyFacts` becomes build step 6, after the content store and read primitives. No new dependency. No findings F-entries: the bundle and `replyFacts` are unbuilt, and no new evidence was gathered.

### Decision: sharded trail layout, no migration; weekly content sweep, prune stays explicit
**Date**: 2026-11-09
**Status**: Accepted (owner: hamr0)
**Context**: The prune POC ([poc/m3-prune](../../poc/m3-prune/README.md)) showed that a flat `records/` makes every commit write a git tree with one entry per record, so a one-commit-per-record trail is quadratic in git's own storage; [F24](findings.md) has the measurements. Separately, the automatic content sweep ran daily, which is more often than a retention window of years needs.
**Decision**:
1. **Shard by the first two hex chars of the id.** `records/<id[0:2]>/<id>.json` (+ `.json.ots`) and `replies/<id[0:2]>/<id>.<slug>.json`; `keys/` unchanged. Options: keep flat and accept the cost; shard by 3 chars; shard by capture month. **Two chars (256 directories)**: a commit's tree write drops from O(N) to O(N/256), the shard is derivable from the id alone (no clock, no lookup), and 256 directories stay cheap to list.
2. **One layout, no migration.** Options: a flat-layout reader, a `migrate` command, a flag. **None**: nobody uses mailproof yet, so a second layout would be pure cost. A trail with `records/<32 hex>.json` directly under `records/` fails with `ERR_TRAIL_LAYOUT` (re-create it). Every path is built and parsed in `src/proof/layout.js`.
3. **Automatic content sweep weekly, configurable** (`content.sweepDays`, default 7). Content lives between `days` and `days + sweepDays`. No timer: the next `sync()` after the interval runs it; an explicit `expireContent()` always runs.
4. **Prune is never scheduled.** It rewrites history, so it stays an explicit command.
**Consequences**: SPEC B3, B5, B6, B7 updated; M3 prune (step 3) is built on the sharded layout. The pre-M3 flat layout of 2.2.x is not readable by the next release (CHANGELOG at release time).

### Decision: prune mechanism details (M3 step 3), mechanism-level forks
**Date**: 2026-11-09
**Status**: Built, shipped in 3.0.0 (mechanism forks decided by the implementer inside the owner's brief: fast-export / fast-import, no lock during the build; the two items marked "product-visible" are for the owner to confirm)
**Context**: Building prune on the POC's recommendation ([F24](findings.md), [F25](findings.md), SPEC B9) forced a few choices the POC did not need.
**Decision**:
1. **The notice describes the snapshot.** The pruned trail is built from a snapshot HEAD without the lock, and the notice is its root commit, so it cannot be written after the commits made during the build are known. Its counts and `previous-head` are the snapshot's; the result and the backup carry the final numbers. Options: build under the lock (rejected by the owner: blocks writers); rewrite the notice at the end (changes every commit id again, the cost the unlocked build avoids).
2. **Late key rule.** A kept record made during the build may name an archived key first committed before the cutoff that no record kept at the snapshot names, so it is not in the notice. The key is added to that record's commit. Options: abort and rebuild (a rare collision costs the whole build); carry every prefix key (defeats dropping keys).
3. **The journal is written only under the trail lock**, at the swap, so a build in progress is never mistaken for a crashed one by another process. Recovery is a hook inside `withTrailLock` for the trail lock (a dynamic import, so there is no module cycle).
4. **The swap waits for a running sync** (up to the 30-minute sync cap plus a minute) instead of failing fast like a sync does: a failed wait would throw away a build that takes minutes. A sync that starts during the wait fails fast as usual. Product-visible: a prune can sit behind a long sync.
5. **A cutoff that would remove every record is refused** (`ERR_PRUNE_CUTOFF`), a cutoff that removes nothing is a no-op. Options: allow an empty trail. Product-visible: refused because an empty trail with only a notice is more likely a mistyped date than an intent.
6. **No all-commits checker inside `prune()`.** The POC's checker takes 109 s at 20k; the shipped guard compares the file set (and the net change of late commits) from `ls-tree` / `diff-tree`, and the full checker is a test helper.
**Consequences**: SPEC B9 documents each; F25 has the measurements.

### Decision: M3 CLI: menu + subcommands, one config file, explicit account, no daemon
**Date**: 2026-11-10
**Status**: Accepted (owner: hamr0); built (SPEC B11), shipped in 3.1.0
**Context**: M3 step 5 (decisions-log "M3 scope" item 10 fixed only "one CLI, menu, config, MCP"). The owner decided the shape of the CLI and config; the spec author listed what was left to decide in SPEC B11.12.
**Decision**:
1. **Menu and subcommands share one code path.** `mailproof` with no arguments is a stdlib readline menu; each item prompts for its parameters with hints, defaults and re-prompt on bad input, then runs the same command function as the subcommand (`mailproof prune --account work --before 2026-08-19`). 2. **No daemon.** No start/stop/restart and no background process of mailproof's own. `watch` is a foreground long-running command (poll, default 5 min; IDLE is a later option); docs show systemd --user and cron. Options: a self-daemonising watcher (pid files, stale state, an upgrade story); rejected, the init system already does that.
3. **One config file** `~/.config/mailproof/config.json` (XDG, `--config` override) with `accounts` keyed by name (not `accounts.json`); secrets by reference only (`passCommand` | `passFile` | `accessTokenCommand`), a plaintext password field is refused; refused with EX_NOPERM 77 unless owned by the user and mode 0600. 4. **Explicit account.** With more than one account every command needs `--account`; the menu asks. Never "all accounts" implicitly (personal and business stay apart on purpose); `status` is the read-only exception.
5. **Commands:** `sync`, `watch`, `list`, `show`, `verify`, `replies`, `check`, `forget`, `prune`, `backup`, `status`, `update`, `config`, `help`; `export` is listed as needing M6; `mcp` reserved for step 6; `mailproof-sync` unchanged.
6. **Destructive:** `forget`, `prune` need `--yes` as subcommands, the typed account name in the menu; both show a dry-run summary first.
7. **`backup`:** a git bundle of the trail (restore = `git clone`), optional separate content archive, `--push` to `backupRemote` only when invoked, with a warning that proofs hold signed headers (addresses, subjects). Content archive via the `tar` binary (stdlib has no tar writer; a private format would be unreadable elsewhere).
8. **Output and codes:** human by default, `--json` one document per command; exit codes as `mailproof-sync` (0, 64, 75, 77) plus `2` for "ran, answer is no" (`verify`, `check`).
9. **Help text from the same JSDoc as `primitives.json`**: a generated help table checked by `npm run check:cli-help`, like `check:primitives`.
10. **`update` prints `npm install -g mailproof@latest`; `--run` executes it.** A global install may need root or come from another package manager.
11. **No new runtime dependency.**
**Consequences**: SPEC B11 (with an "Owner review" list); PRD §7 M3 Interfaces aligned (`config.json` with `accounts`). Step 5 would add two small library pieces, `upgradeStamps()` and `prune({ dryRun })`, if the owner confirms B11.12 items 4 and 5. Build order after this: MCP (step 6) reads the same help table.

**Owner resolutions of the review list (2026-11-10)**, final (SPEC B11.12): (1) the `update` subcommand prints the command and runs it only with `--run`; the menu item asks `y/N` and then runs `npm install -g mailproof@latest`. (2) The content backup is a separate unencrypted file made by the `tar` binary. (3) `backup --push` never forces; the remote keeps the history from before a prune as an archive, and a rejected push is explained and exits non-zero. (4) A small public `Mailproof#upgradeStamps()` is added (the library gains one method so "Sync now" and `status` can upgrade OpenTimestamps stamps). (5) `prune({ dryRun: true })` is added so the dry-run summary is the library's own computation. (6) `config add-account` is an interactive wizard that writes the config (0600, atomic, other accounts kept, never a plaintext password) after an explicit confirmation, not a print-only helper. (7-13) as the defaults in B11.12. What the build decided beyond the spec is in SPEC B11.14.

1. **Stdlib, no MCP SDK** (F29). Revisit only if resources, prompts, HTTP transport or OAuth come into scope. Options: the official SDK (a fifth runtime dependency for about 100 lines of protocol code; rejected).
2. **Tool names = library method names** (`replyFacts`, `get`); descriptions come from the same JSDoc as `primitives.json` and the CLI help (`@when` + `@fails`, shortened by an optional `@mcp` tag where the library text is too long or too library-specific: a mechanism choice); schemas come from one table `src/mcp/tools.js`, with a generated file and a completeness check like `check:primitives`. Options: CLI command names (rejected: a second vocabulary), hand-written descriptions (rejected: a second source of truth), mechanical truncation (rejected).
3. **All primitives an agent needs, all always listed, no server-side tier switch.** 22 tools: 16 read (incl. `accounts`), 4 write (`record`, `replyText`, `sync`, `upgradeStamps`), 2 destructive (`forget`, `prune`); `close`, `expireContent`, `hashDocument` and the constants are not tools. Every tool carries `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` and a `title`, set conservatively, because the owner scopes tools in the client by the hints. Options: tiers `read`/`write`/`all` in the config (proposed, rejected by the owner), read-only only (the old PRD rule), a hide-by-config switch. The server adds, for `forget` and `prune`: preview by default (the library's own `dryRun`) and `confirm: true` to act, and an audit line; MCP elicitation is the later real human gate (needs a POC). Reason: an MCP server cannot prove a human is present, so the client's hint policy is the gate and `confirm` only makes the model show the preview.
4. **One server for all configured accounts** (reversing the proposal of one server per account): an `account` argument on every account-bound tool, optional with one account configured and required otherwise like the CLI's `--account`; an `accounts` tool; one `Mailproof` per account opened lazily and closed at shutdown, sharing one worker (same worker options), so memory does not grow with N. `--account X` at launch may restrict a server to one account. Options: one process per account only (rejected as the only shape: N registrations).
5. **Replies are JSON as text content** for every tool except `rawEmail`/`attachment` (an embedded base64 resource under a size cap, or `saveTo` into `mcp.outputDir`); `structuredContent`/`outputSchema` wait until output schemas can be generated from the JSDoc.
Also: `path` inputs are refused until `mcp.inputDirs` is set (`base64` always allowed); no file is written by default; the `mcp` config block holds the 512 KiB response and 1 MiB binary caps; `forget` gains a library `dryRun`; `sync` gets a `maxMessages` argument; stderr silent; failures are `isError` results carrying the library code.
**Consequences**: SPEC B12; PRD §7 M3 Interfaces and Open list updated; no new runtime dependency; the config gains an optional top-level `mcp` block; the library gains `forget({ dryRun })` and the JSDoc an optional `@mcp` tag; with no server-side switch, a client that allows everything lets a model delete after a preview (the annotations and the client policy are the gate).
2026-11-11 (later): owner accepts the hints as advisory (F30: Claude Code ignores them); known limit, hint values stand as documented metadata (SPEC B12.3).

### Decision: M4: drop appointments; seal and pair export
**Date**: 2026-11-11
**Status**: Accepted (owner: hamr0)
**Context**: The PRD's M4 was "Appointments" (calendar replies, propose/accept, reminders). The owner's real case is a meeting confirmed between A and B, then later events (a bill of quantities, a possible commission). M3's per-record OTS ran inside the trail lock, and the CLI `export` waited on M6. The PRD M3 open item asked whether pair/thread export is M3 or M6.
**Decision**:
1. **Appointments is dropped as a calendar/iTIP module.** The existing A<->B trail (`list({ with })`, `counterparties`, `linked`, attachment hashes, OTS, key archive) serves the case. An agreement ceremony (send a statement, require a confirm, close) is signedreply/gitdone's Declaration; building it would copy gitdone. Options: iTIP replies and reminders (rejected: not the real need); an agreement ceremony (rejected: scope creep). Known limit, documented not fixed: B's signed reply proves B answered my Message-ID, not what my mail or attachments contained (my Sent copy is unsigned; Microsoft signs From/Date/Subject but not To/In-Reply-To/References and alters bodies, F11). A later idea, not scheduled: a content-hash token in the Subject (the one header Gmail and Microsoft both sign).
2. **New M4 = seal and pair export.** (a) **OTS on by default, stamped per batch.** A stamp job writes a sha256 manifest of the records added since the last stamp plus the previous manifest's hash (a chain), commits it, OTS-stamps it once, and upgrades older pending stamps. Due every 6 hours (configurable); `sync` and `watch` run it when the last stamp is at least that old (like the content sweep's `sweepDays`, no timer); `mailproof stamp` and a library method always run it. A missing `ots` binary never blocks capture (record and flag). Capture no longer stamps inside the trail lock. Options: per record (the old default, PRD §12 Q8; kept as an option); a timer (rejected, no daemon). (b) **Pair export:** `export({ with: [addresses], after?, before? })` and the CLI `export`; the bundle holds the matching records, their keys, reply-text records and the stamp manifests with `.ots`, plus a README; no raw emails or attachments, each record says whether its content is still in the content store. The recipient runs `npx mailproof verify-bundle <dir>`, the same verifier code (options: a standalone copied verifier, rejected as a second source of truth). Export stays off in MCP. No POC: both parts are built from existing parts.
3. **M6 keeps only the ZK part** (`mailproof-zk`), parked until a real user asks; its headers-only export moves into M4.
4. **M5 (hosting your own) is parked.** If revived: a generic "Postfix + OpenDKIM + pipe" recipe, never in the npm package; prior art is knowless `OPS.md` §5 (SPF/DKIM/PTR steps) and gitdone's Postfix pipe transport with exit 75 handling. knowless was asked on 2026-11-11 and declined: it has no MTA or DKIM signer, and hosting would break its auth-mail-only rule.
5. The PRD M3 open item "Pair/thread export: M3 or M6" is answered: M4.
**Rationale**: Prefer the simple path and one source of truth: the trail already holds what the owner's case needs, so what is missing is a strong time seal without lock cost, and a way to hand a counterparty a re-checkable bundle. Batch stamping cuts calendar calls and lock time; the manifest chain keeps order and shows other records only as hashes.
**Consequences**: PRD §7 M4-M6 and §12 Q8 updated; SPEC B13 outlines the wire formats, to be specified at build; B3 and B4.5 (OTS inside the lock, per record) and B11 `export` (exits 64, "needs M6") are shipped text that M4 changes. After M4 the v2 promise (§1, §2) is met; "I sent you this" without a reply stays partial until signed own sends exist (M5). OTS time becomes "no later than", up to the cadence after capture; the git commit keeps the exact capture time.

### Decision: M5: a record command and a self-hosting guide, not a Docker image
**Date**: 2026-11-11
**Status**: Accepted (owner: hamr0); guide written, command specified (SPEC B14), not built
**Context**: M5 ("hosting your own") was parked on 2026-11-11 with the options "a generic recipe, a privcloud module or a Docker image". Signed copies of what the user sends need the user's own MTA to sign, and a way to pipe mail in and out into `record()`. The gitdone operators (real box, 2026-11-11) supplied the Postfix/OpenDKIM facts and one test: a locally delivered copy of an outbound mail carries a valid DKIM-Signature.
**Decision**:
1. **Two deliverables:** a CLI command `mailproof record --direction in|out` (stdin to `record()`, SPEC B14) in the npm package, and a step-by-step guide `docs/product/self-hosting.md` for Postfix + OpenDKIM. After M4.
2. **No Docker image.** Options: an image (rejected), a privcloud module (rejected: a second place to keep current), a recipe only with no command (rejected: every user would write the same stdin wrapper).
3. The guide marks every step proven or UNVERIFIED, and uses the multi-domain OpenDKIM form with an explicit `SignHeaders` (the default signs no Message-ID).
**Rationale**: The hard parts are DNS, PTR, port 25 and IP reputation, none of which a container can set; an image would also make mailproof a mail-server product that must be patched. The command is the one piece that is code, tiny, and shared by every user. Simple path, one source of truth.

Postfix bounces sysexits codes (64, 77), so the guide's wrapper maps every failure to 75 rather than the command changing its codes.

### Decision: MCP parity with the CLI (export through MCP with a confirm gate)
**Date**: 2026-11-12
**Status**: Accepted (owner: hamr0: "MCP should be on parity with the CLI"); built on `feat/m4-export` (SPEC B12.3, B12.5 item 2a, B13.2.1a, B11.6)
**Context**: The MCP server (3.3.0) offered 24 tools. The CLI had five more actions that fit an agent: `status`, `stamp`, `verify-bundle`, `export` and `backup`. The PRD and B12 said "no export or send through MCP without a human gate", `stamp` was deferred (B13.1.9) and `export` was "deliberately not in MCP" (B13.2.1): an agent that could hand a counterparty a directory with the addresses and subjects of a whole exchange, unasked, is a leak.
**Decision**:
1. Five tools, named like the library methods: `status` (read), `verifyBundle` (read, account-free), `stamp` (write, open-world, idempotent), `export` (write, not idempotent) and `backup` (write, open-world, not idempotent): 29 tools in all (20 read, 7 write, 2 destructive). Not tools, with a reason each (B12.3): `watch` (a loop), `config add-account` (interactive, handles the secret), `update` (folded into `status`: version and the upgrade command, never run), `help`, `mcp`.
2. **The rule "no export through MCP" is reversed for export** (and `backup` follows it), with a gate: without `confirm: true` they return a preview built by the library's own dry run (`export({ dryRun })`, new; `backup({ dryRun })`, new) and change nothing; the export preview lists the emails and states what leaves (addresses and subjects of the exchange, signed headers, keys, seals; other records only as hashes; no bodies; completeness not proven). With `confirm: true` they write only under `mcp.outputDir`, under a plain name (no path, no separator, never absolute); the library already refuses to overwrite or follow a symlink. `push` needs `confirm: true`, the account's `backupRemote`, is never forced and contacts that host.
3. The data parts move into the library so the CLI and MCP render one result: `Mailproof#status()` and `Mailproof#backup(opts)` (the remote is an option; the library holds none). The CLI output is unchanged byte for byte (23 status and backup runs, text and JSON, compared before and after). Account-level facts (state file, config check, version) come from one helper, `accountStatus()` in `src/cli/status.js`, used by the CLI and the MCP `status` handler.
**Rationale**: One definition per concept, and an agent should be able to do what the CLI does where it fits. A preview-then-confirm step makes the model show the person the disclosure; it is not a human gate (a model can pass `confirm: true`), so the real gate stays the client's allow rule by tool name, as for `forget` and `prune` (F30). Writing only under a configured output folder under a plain name keeps a prompt-injected agent from choosing a path.
**Consequences**: `destructiveHint` stays false for `export` and `backup` (they add files, remove nothing); `idempotentHint` false for both (a repeat with the same name is refused); `backup` is `openWorldHint: true` because `push` reaches a remote. The PRD §7/§10 "export through MCP" lines are updated. A later MCP elicitation POC could make the confirm a real human gate. One CLI difference: `backup --push` without `--yes` now reports an existing `--out` before the confirmation text.

### Decision: MCP writes and reads the same ~/mailproof folders as the CLI by default; reverses 3.3.0 off-by-default
**Date**: 2026-11-12
**Status**: Accepted (owner: hamr0, closing every MCP/CLI parity gap the CLI walkthrough opened); built on `feat/m4-export` (SPEC B12.2, B12.3, B12.5, B12.6; B5 `status({ refresh })`)
**Context**: After the CLI walkthrough the CLI wrote everything for the person under `~/mailproof/<kind>/` (exports, backups, saved), showed trust profiles by name with a built-in `default`, printed the real in/out and verified counts in `status`, and knew whether it was a development link. The MCP server (3.3.0) could do none of it by default: `mcp.outputDir` and `mcp.inputDirs` were off until set, `checkProfile` took only an inline object, and `status` returned stale or missing counts and no install facts.
**Decision**:
1. **Folders.** When the config does not set them, the server reads under `~/mailproof` (`inputDirs`) and writes into the CLI's own folders by kind: `export` to `~/mailproof/exports`, `backup` to `~/mailproof/backups`, `rawEmail`/`attachment` `saveTo` to `~/mailproof/saved` (`userDir(kind)`, created 0700 on first use, a preview included). An explicit `mcp.outputDir` / `mcp.inputDirs` replaces the defaults; the one way to turn them off is `"outputDir": null` and `"inputDirs": []`. Unchanged: preview plus `confirm: true`, plain output names only, resolved paths must stay inside the folder (symlink-safe), every write audit-logged.
2. **Profiles** resolve through one module (`src/cli/profiles.js`: built-in `default`, `<configDir>/profiles/<name>.json`, the listing with one-line summaries) for the CLI and MCP. MCP `checkProfile.profile` takes a name or an inline object and defaults to `default`; a new read tool `profiles` lists them (no library method: the config directory is a CLI-layer fact, like `accounts`).
3. **Status** moves the CLI's index catch-up into the library as `status({ refresh: true })` (500 ms lock wait, falls back to the read-only answer); the CLI and the MCP tool both use it, so they return the same numbers.
4. **Install facts** come from one detection (`src/cli/install.js`, shared with `update`): MCP `status` returns `install: { kind: 'dev-link' | 'npm', path }`; the npm version lookup stays CLI-only (`update --check`).
**Rationale**: One definition per concept, and an agent should be able to do what the CLI does where it fits. The 3.3.0 "off by default" rule protected against a prompt-injected agent reading `~/.ssh` or writing anywhere; the new defaults keep that property because the read folder is `~/mailproof` (never the home directory) and the write folders are the three the CLI already owns.
**Consequences**: A minor bump: after upgrading, the server reads under `~/mailproof` and writes there without any config (CHANGELOG "Upgrading from 3.3.x"; set `outputDir: null` and `inputDirs: []` to keep the old behaviour). The tool count is 30. `~/mailproof` also holds exports and backups (other people's addresses), so anything an agent may read there is readable by it.
